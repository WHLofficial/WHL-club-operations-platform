## 一、现状体检（全部为生产实测，2026-10-17）

### 1.1 机制

| 维度 | 现状 |
| --- | --- |
| 表 | `venue_bookings(club_id, season, window_seq, slot_no, activity_type, booked_by, created_at)`，UNIQUE(club_id, season, window_seq, slot_no) |
| 档位 | `activity_slots`（config，缺省 **2**，clamp 0–20）；`slot_no` 是**窗口内抽象序号**，与真实赛历无关 |
| 活动目录 | `activity_config`（config，缺省即生产在用）：演唱会 3–8m / 15% 概率 2–5m 草皮损坏；电竞赛事 2–4m；球迷开放日 0.5m；青训夏令营 1.0m×（1+0.1×青训级）；空置 0 |

| 随机 | `seededUnit([club, season, window, slot], draw)` 确定性伪随机（FNV-1a + splitmix32）⇒ 同档位逐字恒定、可复现、无重掷空间 |
| 加成 | 草皮级：损坏概率 ×(1−0.15L)、演唱会收入 ×(1+0.1L)；青训级：夏令营收入 ×(1+0.1L)；头部品牌 attendBuff +2% |
| 闸门 | ① 窗口必须开着（否则 409「这一窗已经关了」）② `assertOpOpen('consumption')`（v6.49.0 运营时刻表；当前 11 个 op 全 none = 放行） |
| 联动 | 事件池只有 2 条 requires_activity=concert：`guest_ghost`（嘉宾鸽了）、`concert_pack`（爆满加场） |
| UI | 消费中心 `BookingsCard`：一张表（档位/已排活动/预计收入/改排为/排上）；关窗只读；0 档位提示 |

### 1.2 生产实况（whl-club remote，2026-10-17）

- **`venue_bookings` 0 行**；**18 队 × 5 设施（commercial/broadcast/pitch/youth/medical）全部 0 级**；
  ledger 里 **`activity` / `maintenance` / `naming_fee` / `luxury_tax` 四种流水一条都没有**。
- `season_windows` 只有一行：S9 W1，**status=closed**，opened 2026-09-18T01:00 → closed 01:01（一分钟，且 audit_log 无 window_open/close 记录 ⇒ 不是走开窗接口建的）。
  `loadWindowRef` 只认 `status='open'` ⇒ **当前没有开着的窗口** ⇒ 档期/设施/冠名**整层场外经营从未真正跑起来**。
  **（2026-10-19 订正）** 这一行不是「运营开了 1 分钟」：`scripts/prod-20260920-s9-window-baseline/01-window-baseline.sql:28-30` 直接 INSERT `status='closed'` + 两个字面量时间戳；同目录 README 自述「不经应用开窗」「不写审计」「不跑关窗批」；`seasons.status` 仍 `preparing`。⇒ 准确表述是**从未经接口开过窗**，不是开了一分钟后关掉。
- 运营时刻表 11 个 op 全部 `start_anchor=none, end_anchor=none` ⇒ 闸门放行，唯一拦路的是「窗口没开」。

### 1.3 现行玩法的三个硬伤（数字）

**(a) 没有决策：演唱会是支配策略**

| 活动 | 期望收入 | 期望草皮损坏 | 期望净额 | 备注 |
| --- | --- | --- | --- | --- |
| 演唱会 | 5.50 | 0.525 | **4.98** | 草皮级越高越强（L=5：8.25 − 0.13 ≈ 8.12） |
| 电竞赛事 | 3.00 | 0 | 3.00 | 永远次优 |
| 青训夏令营 | 1.00–1.50 | 0 | 1.00–1.50 | 只有收入轴 |
| 球迷开放日 | 0.50 | 0 | 0.50 | 只有收入轴 |
| 空置 | 0 | 0 | 0 | — |

⇒ 最优解 = 「两个档位都排演唱会」，每窗两次点击，零成本、零后果、零风险决策。除演唱会损坏概率外没有任何非金钱效果。

**(b) 量级与真实感都不对**

- 演唱会收入与**容量、死忠、城市、对手、天气完全无关**：12000 座和 100000 座同价。
- 演唱会期望净额 4.98m ≈ **2.6 场主场收入**（S9 W1 主场平均 1.89m，99 场共 186.75m）。
- 档期没有成本栈（制作/安保/宣传/场地搭建），是一条纯水龙头；草皮损坏是唯一下水道，且**只影响钱**（上座公式里没有草皮项）。
- 平台侧没有比赛日日期，只有 `round` + `finished_at` ⇒ 现行「非比赛日」只能做成抽象序号。

**(c) 节奏太稀 + 入口太深**

- 每赛季**最多 2 个常规窗**（`openWindow` 硬拦第 3 个；临时窗不扣工资）+ 每窗 2 档 ⇒ **一个赛季 4 次决策**。
- S9 W1 规模：116 场确认（冠军杯小组 30 + 顶级联赛 54/9 轮 + 次级联赛 32/8 轮），每队 4–7 个主场。
- 入口在消费中心一张表里，关窗只读，没有提醒 ⇒ 0 采用率。

## 二、发散改进菜单（按轴，含先例）

1. **经济底盘：容量驱动 + 成本栈**（先例：Football Manager 非比赛日收入、热刺球场/NFL 双用、伯纳乌演唱会）
   收入 = 容量 × 售票率 × 票价 × 场馆分成 × 城市/声望系数；成本栈 = 制作 + 安保 + 宣传 + 搭建（占收入 40–60%）。
   小场（12000）演唱会净 0.5–1.5m、大场（60000）3–6m ⇒ 与容量/扩建挂钩，风险对等（可能净亏）。
2. **活动菜单按轴分化**（先例：Hades 一种货币一条轴）
   演唱会=钱/草皮磨损；电竞=中钱+年轻球迷+转播协同；开放日=死忠/球迷情绪；夏令营=青训进度/社区；
   新增企业日/商业活动=品牌 satisfaction（需商业区等级）；空置=草皮恢复。每项一个主轴 ⇒ 无全能最优。
3. **草皮成为持久状态**（先例：FM 草皮状况、真实演唱会毁草皮）
   condition 0–100：演唱会 −15…−30、比赛 −2…−5、雨雪加倍、每轮 +N（草皮级提高恢复）。
   后果只落在平台能管的东西上：上座/商业收入乘数、球迷情绪、球员状态（若有建模）——比赛模拟在赛事系统，不能碰。
4. **日历与档期绑定（轮次为单位）**（先例：FM 赛程拥挤、赛车经理赛历）
   slot 绑到「第 N–N+1 轮之间」：与下一场主场的间隔决定恢复、冬季/露天天气风险、同日冲突。
   预订改为**滚动**（赛季中随时可订未来档位）⇒ 同时修掉「整层场外经营因窗口未开而全黑」。
5. **风险与保险**（先例：伯纳乌 2024 噪音诉讼、Two Point Hospital 事故）
   票房不足（需求掷）、天气取消/延期、噪音投诉累积（可投资隔音缓解，硬上限场次）、安保事件（医疗级缓解）；
   保险作为可选购买项（保费 × 覆盖范围）。
6. **竞争与市场层**（先例：真实巡演档期、赞助激活）
   联赛级「演出池」：每窗 1–2 个 A 级演出，容量+声望门槛，先到先得或暗标；区域分流需要城市字段（clubs 只有 country）⇒ v1 跳过。
7. **声望与进阶**（先例：Stardew 愿望型下水道、主题公园评奖）
   场馆声望 0–100（来自演出成功度/上座/球迷情绪）⇒ 解锁演出等级（地方乐队→明星巡演→国际巨星）、冠名溢价、主办联赛活动；
   愿望型下水道 = 场馆升档（3/4 档）+ 演出专用设施（舞台/隔音）。
8. **曝光与可用性**（采用率是交付前提）
   独立「场馆经营」页签（日历 + 草皮表 + 收益预估 + 球迷情绪）替代消费中心里的一张表；
   未排档位提醒（「本窗 2 档未排 ≈ 损失 10m」）、一键推荐、首用引导。
9. **既有系统联动**
   死忠（开放日→fans→上座→一切）、冠名（演出曝光→satisfaction/热度→续约与溢价、行业匹配）、
   五设施各接一条收益线、事件池从 2 条扩到 ~10 条、天气季节性、rumors 模块喂「巨星想来开唱」。
10. **阀门与监控**（Mirela 口径）
    参数已全部走 config ⇒ 补管理端面板（每窗活动收入、top 队、水龙头集中度告警）与回滚能力。

**Q1 - 定位**：这个系统的第一目标是什么？(a) 决策深度（每轮真做取舍）(b) 真实感/叙事 (c) 财政平衡工具（在奖金与工资之间加一条可变收入）(d) 曝光/参与度。

**Q2 - 节奏与结算**：档位按什么节奏排？(a) 维持每窗 2 档（4 次/赛季）(b) 每轮间 1 档（6–10/窗）(c) 每窗固定池扩到 6–8 档 (d) 滚动日历随时订未来档位。
➡️ 推荐 (b)+(d)：轮次是平台唯一的日历单位（没有真实比赛日期，只有 round + finished_at）；事件在轮间结算，窗口关闭只做对账。4 次/赛季撑不起玩法。

**Q3 - 经济底盘**：(a) 保持现在的绝对收入区间 (b) 容量/球迷驱动 + 成本栈 (c) 容量驱动但不加成本。

**Q4 - 草皮**：(a) 维持只赔钱 (b) 引入持久 condition 并影响上座/收入/情绪。
➡️ 推荐 (b)——单条杠杆最大的改动；但它**不能影响比赛本身**，定位见第四节（用户追问后的修正版 Q4 也在第四节）。

**Q5 - 活动轴**：你希望活动分别服务哪些轴？（可多选）钱 / 死忠 / 青训 / 品牌 / 年轻球迷+转播 / 草皮恢复。
➡️ 推荐六轴全要，每项一个主轴，保证没有全能最优。

**Q6 - 曝光与可用性**：(a) 留在消费中心那张表 (b) 独立「场馆经营」页签 + 未排提醒 + 一键推荐 + 滚动预订。

## 四、可行性追问（用户 m18210）：草皮状况在 FC 系列模拟下能落实吗

**结论**：分两半——「影响比赛本身」不能；「影响平台自己的系统」能，而且钩子已经在代码里。

### 4.1 不能的那一半

- 比赛由玩家在 FC26 里自己踢，联盟系统只收结果与截图（赛事仓）；平台对游戏没有任何写入/干预通道，
  FC26 也没有可被外部设置并强制的「草皮状况」参数。
- 所以「草皮差 → 打滑 / 传球失误 / 主队优势变化」这类效果一律做不到；靠规则约束（「草皮差必须申报」之类）
  也不可验证，不建议。

### 4.2 能的那一半（四条杠杆，均有现成落点）

1. **上座与主场收入** —— 上座公式是平台唯一真源 `src/core/attendance.ts`
   （demand = fans × multiplier × tierCoef × form × wx × opp × nextAttendanceMod × perturbation），可插入草皮乘数；
   同类先例 = `stadiums.next_attendance_mod`（`src/db/migrations/0049_stadium_event_pending.sql`，
   随机事件经 `src/worker/event-ops.ts:844` 写入，下一场消费后清零 `src/worker/home.ts:460`）。
2. **球迷与品牌** —— 关窗时的死忠演化与品牌 satisfaction 演化都由平台计算（`src/worker/home.ts` 关窗批 + 品牌池），
   草皮长期差可压低死忠增长与品牌满意度。
3. **档期经济自身** —— 草皮级已影响损坏概率与演唱会收入（`src/worker/venue-ops.ts:144-147`）；
   把「级」扩展成「级 + condition」即让出租与养护成为真取舍。
4. **伤停** —— 有数据基础但**不在平台手里**：`injury` / `injury_miss` 属赛事库，平台只读
   （`src/worker/player-matches.ts:132-134`「赛事库一律只读」），写通道只有 team-upsert / team-rename
   （`src/worker/tourClient.ts`）⇒「草皮 → 更容易受伤」需要赛事仓新增写入通道（跨仓），
   或平台自建一层伤病（与玩家已见的「缺阵（伤病停赛名单）」口径重复）⇒ **v1 不做，列 P2 跨仓议题**。

### 4.3 定位重述

草皮不是**竞技变量**，而是**经营压力**：出租赚钱 → 草皮变差 → 下一场主场上座与商业收入打折、
球迷/品牌不满、损坏概率上升。玩家在钱和口碑上感受得到，比赛结果不受影响。

### 4.4 Q4 修正版

(a) 纯经营压力（推荐；平台内闭环、零跨仓）
(b) 经营压力 + 规则层伤停（跨仓 / 靠规则约束，P2）
(c) 放弃草皮，改用别的杠杆（如档位数量与赛程距离）

## 五、编辑器工具能不能当落地通道（用户 m18222 追问，2026-10-17 研究）

两个工具是两回事，但结论一致：**都不能给「开赛时的比赛」设参数**。

### 5.1 FET = FIFA Editing Toolsuite v2.2.0（fifaeditortool.com）

- 定位：本地**资源/文件**编辑器 + Mod Manager（Frosty Toolsuite 血统，致谢 GalaxyMan2015、Cade、benji、derwangler 等）。
- 能力：贴图 / 网格 / 音频 / 球衣 / 脸型（FBX 导入导出、face donor、批量）/ tifo / 徽章 / 球员专属身体模型；
  做好的 mod 由 Mod Manager 应用到本地游戏安装（已支持 FC 27）。
- 边界：改的是**本地安装里的数据文件**，不是运行时内存；没有「给某一场比赛设天气/球场/草皮」这种入口。

### 5.2 FC 26 Live Editor（xAranaktu）

- 定位：C++ DLL 注入游戏进程、实时改内存。能力清单：Players / Teams / Managers 编辑器、Database Editor（改游戏 DB 表）、
  Transfer History 撤销、转会禁令、阵型与首发、**Match-Fix upcoming games**、Speedhack、**No crowd during matches**、
  Legacy Files、LUA API v2（LOGGER / MEMORY / Transfer Ban / Aardvark / **Gameplay Attribulator** / Localization /
  Player Development / HTTP Requests / Events）。
- **offline only（硬约束）**：README 自带 **EAAC / EA Javelin Anticheat Bypass**（原文 "Runs the game without the
  anticheat. Offline use only."）；wiki 首页原文："This tool doesn't work online. This is intended, and won't be 'fixed'."
  与 "Using the tool may flag your account and EA may ban it later on."
- Gameplay Attribulator（wiki 页，2025-12-04）：可改 `gameplayattribdb` / **`prematchattribdb`** / `perksattribdb` /
  `simulation` / `penta` 这组 attrib（示例：球半径 0.365→3.0），"to test the changes you just need to restart the match"。
  **文档里没有 weather / time of day / pitch / stadium / referee 任何字段**；`prematchattribdb` 只是名字暗示存在赛前组，
  字段清单要装工具才能查。

### 5.3 反证：游戏数据里确实有「天气/球场」表，但属离线 compdata

`templates/LIVE_EDITOR_LIMITS.json`（Live Editor 给 mod 作者的 compdata 上限表）列了
`MAX_FCEDATA_WEATHER: 420`、`MAX_FCEDATA_STADIUM: 100` ⇒ FC 的数据模型里天气/球场是**赛事数据（compdata）实体**，
但那是离线/生涯模式的数据，靠 mod 打进本地安装。

### 5.4 结论（对草皮方案）

1. **编辑器路线关闭**：没有任何工具能把「草皮状况」变成 FC26 里影响比赛的真实变量（游戏里根本没有这个机制可设，
   只有视觉草皮磨损）。
2. **线上比赛两条路都不通**：Live Editor 明说不能线上用（要关反作弊才能跑 = 封号风险）；FET 改本地文件，
   线上模式用服务器数据（贴图类本地资源可能仍显示，球员/球队/赛事参数不会跟本地改动走，更不可能只对一方生效）。
3. 游戏内的「开赛因素」（球场 / 时段 / 天气 / 半场时长 / 球 / 裁判 / 镜头）是**比赛设置界面**自己选的，
   编辑器工具管不到 ⇒ 若要做「草皮在游戏里可见」的规则层，只能借这些界面项 + 开赛前截图自证。
4. 顺带（联盟完整性）：这些工具**不威胁联盟线上比赛**——它们不能在线上模式运行，所以不存在「用工具改比赛」的通道；
   唯一新增的风险是「有人本地改数据后跑离线比赛截图」——但那和现在用离线打 AI 出图没有本质区别。
5. 用不上的彩蛋：Live Editor 的 LUA API 有 HTTP Requests（能调外部 API），理论上可让离线比赛与平台联动，
   但离线场景不存在。
6. 未验证项：① 线上好友赛开赛前能否选球场/天气/时段（搜索引擎全部被劫持成中文市场结果，取不到第三方资料；
   游戏内界面才是权威 ⇒ 需用户确认）② FC26 是否存在影响球的草皮机制（工具文档无任何证据）。

### 6.4 收入与成本（规模驱动）

- `income = base(活动) × capacityFactor(容量, 死忠) × 饱和系数 × (1 + 设施加成) − cost(容量)`
- `capacityFactor` 以联盟中位容量为 1.0（小球队 <1、大球场 >1）；`cost` = 安保/搭建/清洁，演唱会 > 电竞 > 开放日 > 青训营

### 6.5 市场饱和（杀支配策略）

- 同活动在本队本窗重复：第 2 场 ×0.7、第 3 场 ×0.45（同一批观众不会连看三场）

- 效果：最优解从「全排演唱会」变成「按球迷情绪与市场配比排」

### 6.6 后果落点（可见的记忆，玩家自己能看见）

## 八、窗口节奏与自动化（下一问，全功能阻塞项；2026-10-20 修订）

### 8.0 两个轴，不要捆成一个问题

- **轴 A：节奏 / 时长** —— 一个赛季开几个窗、每窗多长。候选 **W1–W5**。
- **轴 B：自动化** —— 谁负责开窗、谁负责关窗。候选 **B1–B4**。
- **为什么拆**：观测到的失败是「窗口从未开过」（生产 `season_windows` 无 open、`venue_bookings` 0 行；S9 W1 是造数工件）。**只自动关不能修这个失败模式** —— 没人开窗时，自动关没有对象。轴 B 必须回答「谁开、开失败怎么办」。
- 两个轴独立：可以 W1（2×7d）+ B1（自动开 + 自动关），也可以 W1 + B3（人工开 + 站内提醒）。Q6 的「场馆经营页」是曝光层，不替代开窗动作。

### 8.1 为什么必须先定它

Plan A 只定义了「每个开着的窗口给多少档」，没有定义「一个赛季开几个窗、每窗开多久」。而：

- **季决策点 = 槽位 × 窗口数**；Plan A 的 4/6/8 是「2 个常规窗」口径，窗口数一变全部作废。
- **收入、工资、合同刻度、维护费、冠名、忠诚支出全部以窗口为边界**：
  - 工资 + 富人税在关窗批（`src/worker/window-machine.ts:300` → `src/worker/window-payroll.ts`）；1 个常规窗 = 0.5 赛季（`window-payroll.ts:2-4`）。
  - 合同效力 = 0.5 × 已关常规窗数（`src/worker/contract-ticks.ts:5`、`:30-45`）；保护期 = 签约基数 + 3 个常规窗（`src/core/bypass-rules.ts:14`）。
  - 基础维护费按「本窗主场场次」收（`src/worker/home.ts:602-628`）；赛果归窗取在开窗（`src/worker/results.ts:226-233`）。
  - 忠诚支出只在同赛季第 2 个常规窗扣（`window-machine.ts:310-315`）。
- **现状是 0，不是「少」**：生产 `venue_bookings` 0 行、当前无开窗；全库唯一一条 S9 W1 是造数工件（见 §1.2/§7.0）。**从未经接口开过窗**。
- **O1 的副作用**：整季开窗 ⇒ 8 个转会键 + `consumption` 的代码层窗口闸整季开放（`venue-ops.ts:237`、`routes/market.ts:228/968`、`offers.ts:639`、`bypass.ts:92/297/382/466/635/686`、`activations.ts:58`、`stadium-ops.ts:120/192/260`、`registration.ts:243`、`shop.ts:98`、`sea-sealed.ts:276`）。若选 O1，必须额外定「赛季中转会截止」规则，不能只靠「开 1 窗」。

### 8.5 推荐：W1 + B1（2 常规窗 × 7 天，自动开 + 自动关）

> **2026-10-20 答复覆盖：B1 作废，实际 D（随转会窗/管理端/ops_schedule）**。本节的 W1 节奏与数字仍有效；自动化部分（`window_plan`、tick、`cron_tick`）仅作历史方案保留，不再实施。

**理由（按可靠性排序）**：

1. **保住 2 窗经济日历**：工资 2×（2044.8）、合同刻度 +1.0/季、保护期按 3 窗、冠名 2×、忠诚在第 2 窗扣。W4 少收一半工资、刻度只走 +0.5、忠诚永不触发、档位腰斩；W5 的 7 个临时窗冻结工资/刻度/冠名。
2. **现金不越界**：档期 89.4–121.6 m/季 = 奖池的 **7.9%–10.8%**，符合 Q1「补充收入」；W5 的 355–483（31.6%–42.9%）背离定位。
3. **现金流最不坏**：2 窗方案里 W1 的季内最低 −63.4，W3 是 −73.8、W5 是 −78.2。
4. **决策量可承受**：4/6/8 次/季；W5 是 18/27/36 次，且每次关窗都要清三道硬闸。
5. **B1 直接修「从未开过」**：自动开 + 自动关，配失败通知；B2 只自动关、B3/B4 仍依赖人工，不能修这个失败模式。

**必须同时承认的弱点**：

- 现金优势依赖 u：最优混合下 u<65%、全排演唱会下 u<88.4% 时，W4 的「档期收入 − 维护」不差于 W1。**W1 的主论据是工资/合同刻度，不是现金。**
- 7d/窗 = 14 天/季转会市场开着（按 35 天赛季假设约 40%）；若产品要短转会期，只能 W2/W3，档期与最穷队现金流随之变差。
- 2 窗上限不变 ⇒ 每季最多 4/6/8 次决策，「漏一次等半个赛季」仍在。
- 小球队 2.99/季（u=0.85、§7.1 青训 1.0）可能理性忽略档期；若 Q9-A 把青训压到 ≤0.2，小场降到 2.21（−26.1%），矛盾更明显——Q9-A'（青训 0.7）是折中（2.48，−17%）。
- **B1 的自动开窗有「开错时点」风险**：必须有 `window_plan` 合法性校验、管理员可见的排期、开窗失败/计划缺失的通知，以及撤销入口；不能静默发车。

**自动开/关窗的实现边界（P0 必须写进 Q12）**：

- **自动开**：新增 config `window_plan`（season / seq / open_at / close_at，或「第 N 轮赛果确认后」）；5 分钟 tick 检查到点开窗。计划缺失/不合法 ⇒ 不发车、通知管理员。
- **自动关**：到点调用 `closeWindow`；撞三闸（`window-machine.ts:265-295`）⇒ **通知管理员 blocker**，不要静默重试。
