## 背景与体检结论

「徽章」=「发放所得的 PlayStyle」，同一域概念被拆成三份存储、两套名字：

| 存储 | 语义 | 主要消费方 |
|---|---|---|
| `game_attrs.PSID1-15` | FC 源快照，导入即整列覆盖（金徽存基础 ID+100） | 球员库/球队页「PlayStyle」列、`?ps=` 筛选、`sort=ps`（0034 索引）、属性页合并清单一半 |
| `players.badges_silver/gold` | 台账计数，起点 0、只数发放所得 | 「徽章」列、`badges_*_min`/`badges_none` 筛选、`sort=badges`（0036 索引）、球员页头部 🥇×2 |
| `player_playstyles`（0031） | 发放明细：槽/kind/基础 ID/source/granted_by | 属性页合并清单另一半、回收/清零/折算、fit（球员页）、跨仓 meta |

分裂实证：球员库同行「徽章」列与「PlayStyle」列互斥各显示半个概念（`club-columns.tsx:203` 只读 15 槽；`players-library.ts:333/342` 两列并存、`:312` DEFAULT_COLS 只带徽章列）；`?ps=` 筛不到发放（`routes/players.ts:478`）而 `badges_gold_min` 不算 FC 自带（`:373-390`）；`sort=ps` 与 `sort=badges` 各数一份；球员页头部计数（`Player.tsx:447`）与右翼合并清单（`:353-357`）两个口径；商店页签叫「徽章」、下拉叫「选 PlayStyle…」。

探针事实（2026-10-30 生产只读）：`player_playstyles` 共 33 行、与 FC 槽同段撞车 0、跨段重复 3 处（见成因留痕）；现状 `?ps=` 生产本就是 `SCAN players`（18,301 行/次，`ps=25` 命中 650）；tour 仓 grep 不到任何 `badgesSilver/badges_gold` 消费（台账改语义跨仓零影响），但 tour fit 的 meta 落库规则「下发非空为准，为空才从 PSID 回填」（`clubMeta.ts:116`）导致有发放徽章的球员丢 FC 槽加分（存量漂移）。

- **Q5**：`?ps=` 扩覆盖用 `players.id IN (SELECT …)` 物化子查询（明细表仅 33 行）；实测照做、预期与现状持平（现状即 SCAN 豁免形状）。

- **Q7**：`/api/players/meta` 的 `playstyles` 数组内容改**全量**（合并清单口径：FC 槽减被抑制 + 明细，形状不变仍是存库 ID 数组）；tour 侧零代码自愈，tour 仓变更记录知会一行。
- **Q8/Q9（最终形态：可逆抑制）**——银/金跨段规则：
  - **择银遇金 → 挡**（任何来源的金，成长/商店/中国计划三路同挡；用户报告的 bug）。
  - **择金遇银**：**商店**挡、提示走「银升金」；**成长**自动**去除银留金**——
    - 发放银（growth/china/shop 来源）→ 同批**删行**（真实删除）；
    - FC 银 → **可逆抑制**：`game_attrs` 槽保留不动，只要该球员存在同基础发放金行，银就在展示/计数/筛选/meta 四口径消失；**金行消失（解约清零/折算删重/回收）的瞬间自动回归**。
    - 金落金槽仍需空槽（替换不释放金槽，槽满照常报错）。
  - 发放银不用抑制的原因：它没有「该回归」的场景——金行的唯一消失途径是解约清零，而解约会把发放银一起清掉，删行与抑制无可观测差异；删行使「删银保金」字面成立且台账公式少一段。
  - 存量处置：**247 删发放银 #24 行**（迁移内 1 行 DELETE）；**557 零数据变更**——FC 银 #1/#31 槽原样保留，派生抑制直接吸收，两枚金保留。
- **Q10（改判单向）**：**外场不可选 GK 项**（基础 ID 51-56，银金两段都挡）；**GK 可见全部 36 项**。清单由 `web/assets/ref/playstyle.json` 的 `type: "Goalkeeper"` 派生，落 core 常量 + 与参照表逐项对齐的测试锁；三路发放服务端同守卫 + 前端选择器同步收窄并提示。存量 33 行零位置违规，只挡新增。
- **Q11（定案）**：被抑制的银在**筛选也不命中**（合并清单口径）。SQL 形状：逐银值 `(槽命中 AND NOT EXISTS(发放金同基础))`——NOT EXISTS 只在槽命中时求值（命中组数百行，非逐行 18,301）；发放银部分在物化子查询内无需排除（顶替时已删行，同基础银金在明细里不可能并存）；读量预期与现状持平，实测验证。

## 核心语义

1. **台账全量计数**：`badges_silver/gold` = **合并清单段内数量** = FC 槽数（减被发放金抑制的银槽）+ 发放明细行数。一次性 backfill（幂等，FC 银槽部分带 NOT EXISTS 排除）+ 写路径改「明细变更后同批重算」：成长 levelup（`growth.ts:660`）/ 中国计划（`:720`）/ 商店买徽章（`shop-ops.ts:322`，**修硬编码 15**）/ 银升金（`:357`）/ 转会回收 china（`transfers.ts:360`）/ **解约（`transfers.ts:771` 修正：重算 = FC 槽数（减被抑制），不再归零**）/ 大换版（`players-import.ts:151` 作废 `(x+2)/3` 折算，覆盖后重算）。
2. **银/金跨段规则**（见 Q8/Q9；三路发放 + 前端选择器全链路；成长择金的确认弹窗标注「将替换已有的银版」）。`game_attrs` **零写面**（抑制是读侧派生，存储不动）。
3. **大换版导入四步序**（`players-import.ts`，单批、确定性、幂等）：① `game_attrs` 整列覆盖（新版数据）→ ② 明细折算（每段留最早 `ceil(n/3)`）→ ③ 同段删重（明细行撞新版 FC 槽则删行，FC 源为准）→ ④ 台账重算（FC 槽数减被抑制 + 留存明细行数）。抑制是派生的：重导带回 FC 银槽自动被抑制规则接住，**无需重放步骤**。
4. **位置资格**（见 Q10；外场可用 30 项 / GK 全部 36 项）。
5. **上限**：唯一出处 = 槽位结构 12 银/3 金（全量口径）；`config.badge_cap_silver/badge_cap_gold` 退役；`china_badges`（发放口径名额）不动。
6. 类型/注释漂移收口：`growth.ts:510` `PlaystyleSource` 补 `'shop'/'external'`；历史迁移注释不改，由新迁移注释收口。
