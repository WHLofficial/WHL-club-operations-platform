## §0 重新排期的三个变化（一句话版）

1. **忠诚方向修正必须提前到「S9 中期窗关窗之前」**。S9 中期窗关窗批就是忠诚首次发放（`src/worker/window-machine.ts:303-310`），而现行代码是 `delta: agg.amount` **正数入账**（`src/worker/season-settle.ts:288-295`），与你的裁决（俱乐部支出）相反。晚一步就多一次**方向相反的注入**：按排程 S9 应扣 −591.65，实际会变成 +591.65，一进一出差 **1183.30**，且会坐实「忠诚奖金」这个名字与账本方向。
2. **杯赛池与联赛入场奖有硬时限，联赛逐场奖金没有**。`prize_table` 是**结算时**读取的（`src/worker/season-settle.ts:111` 加载；`:117-118` 联赛 entry；`:148` `remaining = pool − paid`）⇒ 冠军杯池 200 在 S9 杯赛结算前任何一天改都即时生效；而联赛逐场奖已按场发了 174 笔（`src/worker/prizes.ts`），改单价只影响**剩余场次**、会造成赛季内前后不一致且追不回 ⇒ **联赛重定价只在 S10 生效**。
3. **S9 中期窗就是革命的第一块落地**，不是「先补丁、后革命」。那一扇窗要同时完成：忠诚首扣（首次）、设施首购（3.0M 广播 L1 是唯一人人同回报的投资）、档位 2 档（44.5M 高端出水口）、冠名首签（零现金通道）。窗口时长与招商轮是**前置运营件**，不是收尾事项——S9 W1 只开了 60 秒，物理上不可能成交任何一单。

## 附录 D：冠军杯池的机制实测与下调建议（2026-10-17 追加，回应 T0-7）

> **2026-10-17 二次修正**：用户令「点球决胜按平局重新发」⇒ 代码修正（`src/worker/prizes.ts` `outcome()` 与 `src/worker/season-settle.ts` `aggregateRecords()` 加 stage 闸）+ 生产订正批（净 −3.50M，工件 `scripts/prod-20261017-s9-pk-draw-fix/`）后，S9 小组赛实付由 196.00 改为 **192.50**（4 场点球场由「胜 7.0」改为「双方各 2.5」：收回 21.00 / 补发 17.50）。本附录初稿的「实付 168 / 只省 32」是**错报**（`memo LIKE '冠军杯%'` 少统计 4 笔），下面已按 192.50 全部重算。

**机制（代码级）**
- 逐场即时入账：`src/worker/prizes.ts:173-185` —— 冠军杯小组赛**每胜 7.0 给胜方、每平 2.5 给双方**（`table.champions_group.win/draw`），赛果确认那一刻就发钱；点球决胜场按 `outcome()` 判为胜（`src/worker/prizes.ts:104-109`）——**2026-10-17 已修正**：点球只在**淘汰赛**口径算胜，小组/联赛平比分即平局（用户裁决，同批订正 4 场）。
- 阶段结算只发**剩余池**：`src/worker/season-settle.ts:143-156` —— `paid = Σ(胜×7.0 + 平×2.5)`（同口径、同 CPU 过滤）、`remaining = round(pool − paid, 2)`，**仅当 `remaining > 0 && totalWins > 0`** 才按胜场占比分给「有胜场的队」，memo「冠军杯小组赛剩余池按胜场分配」。
- ⇒ 小组赛支出 = **max(池, 逐场实付)**。池是上限（实付超池时一分不补），也是下限（实付不足时兜底到池）。
- CPU 队不进账：`src/worker/prizes.ts:70-74`（`clubIdByTourTeam` 第 73 行把 CPU 俱乐部排除出映射）⇒ CPU 队的胜/平既不即时发，也不计入 `paid`。
- 入场 15×16 = 240 **未实现**（`champions_group.entry` 在 `src/` 无消费方）⇒ 当前冠军杯总额 = 池 200 + 淘汰 130 = **330**（与 `design-s9-income-system.md` §9 一致；§1 的「570」含未实现的入场 240，是假设值）。

**S9 生产实况（只读，2026-10-17）**
- 小组赛 30 场**已全部打完**（赛事库 tournament 3 / stage id 6 kind='group' n=30）；淘汰赛 14 场（stage id 7 kind='elim'）**未开打**（0 场确认）。
- 30 场构成：25 场比分决胜 + 4 场点球决胜（1-1 点 1-3 / 1-1 点 5-4 / 1-1 点 5-3 / 2-2 点 3-4）+ 1 场弃权 ⇒ 30 场全是「有胜者」，**无真平局**。
- 实际即时付款（**2026-10-17 订正后**）= **25 × 7.0 + 7 × 2.5 = 192.50**（25 胜含 1 场弃权判胜；7 笔平局 = 4 场点球场 × 两侧 − CPU 一侧）——订正前 = 28 × 7.0 = 196.00，其中 3 笔 7.00（流水 id 83 / 256 / 264）已由 `pk_rollback_prize` 收回（−21.00）并按平局补发 17.50 ⇒ 净 −3.50。**初稿的「24 × 7.0 = 168」是错报**：当时按 `memo LIKE '冠军杯%'` 统计，漏了 4 笔非标准 memo（弃权场 #2 的 id 254，以及 3 笔 memo 误写「联赛胜场奖金（比赛 #N，CPU 期补发）」的 #18 id 256 / #22 id 264 / #27 id 257）。
- 结算侧 `paid`（同 CPU 过滤，**修正后的代码口径**）= 25 × 7.0 + 7 × 2.5 = **192.50** ⇒ `remaining = 200 − 192.50 = 7.50 > 0` ⇒ 关窗/结算时再发 **7.50**（0.30/胜，按胜场分给非 CPU 且有胜场的队）。**S9 小组赛支出 = 恰好 200**（旧口径 `paid`=168 会补 32 ⇒ 突破池上限到 228）。

**下调算术（S9 口径，池 200 / 实付 192.50，2026-10-17 重算）**

| 方案 | 小组赛支出 | 相对现在 | 备注 |
|---|---|---|---|
| 池不动（200） | 200 | 0 | 现状 |
| 池 200 → 192.5 及以下（180 / 120 等） | 192.5 | **−7.5（上限）** | 池低于实付后只当上限，再降**一分不多省** |
| 池 120（设计 §3 L0 原值） | 192.5 | **−7.5** | 设计稿按 −80 计（570→490）不成立；初稿「−32」是错报 |
| 池 120 + 胜 7.0→4.0 / 平 2.5→1.5 | max(120, 110.5) = 120 | **−80** ✓ | 逐场实付 25×4.0 + 7×1.5 = 110.5 < 池 120 ⇒ 池成为约束（两旋钮同批才有效） |
| 只动单价、池不动 | max(200, 110.5) = 200 | 0 | **池会兜底回去 ⇒ 单价单独下调无效** |

- 冠军杯总额 330 → 250 时媒体占比 = (1349.16 + 250) / 3278.31 = **48.78%**（仍在 45–55% 带内）；只降池到 120 ⇒ 总额 322.5、占比 (1349.16 + 322.5) / 3278.31 = **50.99%**（几乎不动，仍在带内）。
- 代价提示：逐场 7.0→4.0 直接削减**赛季中现金流**（每胜少 3.0），对 S9 中期窗的支出能力有影响；只动池（−7.5）不影响赛中现金流。

**建议（待拍板）**：若目标是设计稿的 −80 ⇒ **池 120 + 胜 4.0 / 平 1.5**（一次把两个旋钮都动，缺一无效）；若想先小步、不动赛中现金流 ⇒ 只把池降到 120（**实得 −7.5**，比初稿的 −32 少得多——池已几乎不构成约束），并在 T2 杯赛结算前落地（结算时读 `prize_table`）。**重算后的判断**：只动池近乎无效（−7.5），决策重点应放在「是否下调逐场单价」——它是唯一对赛中现金流与赛季总预算同时生效的旋钮。

**附带发现（2026-10-17 已随之消解）**：`src/worker/prizes.ts` 的 `outcome()` 有 `winnerTeamId` 兜底（比分相同且无点球时按 winner 判胜），而结算侧 `aggregateRecords`（`src/worker/season-settle.ts`）没有这条 ⇒ 曾担心「平比分 + 只有 winner_team_id」时即时按胜（7.0）、`paid` 按平（2.5×2）差 4.5。**现已不成立**：同批的 stage 闸把点球与 winner 两条兜底一并限定在**淘汰赛**口径，小组/联赛一律平局 ⇒ 两侧同口径（淘汰赛两侧都不看平局）。
