- 平台现值是 2026-09-19 回填的 **EA 原始队籍**（`scripts/prod-20260919-roster-backfill/`），而 s901 与 `一线队-S9.csv` 是**联盟世界**。

- 对齐归属后，那 84 行变成普通 `create` 行 ⇒ 合同批可整队导入。这就是本批唯一的用途。

## 5. 遗留 304 人是什么（本批不动，但必须知道）

「遗留」= 平台现任（`club_id` 非空）但不在 s901 任何队壳文件里的球员，共 **304** 名（占平台有队籍 551 人的 55%）。它们的去向按 `一线队-S9.csv`（联盟世界全量 24 组）归类：

| 联盟世界所属 | 人数 |
| --- | --- |
| **CSV 里根本没有这些人** | **275** |
| 在解约池 | 11 |
| 布鲁日 | 7 |
| 国际米兰 | 6 |

两点解读：

1. **275 人不在联盟世界的任何一线队名单里**（CSV 734 行 + s901 570 行都不含）。平台把他们挂在某队，联盟世界没有对应席位。
2. **29 人所在的联盟球队平台没有**：布鲁日 / 国际米兰 / 牛津联 / 在解约池 —— 与合同批「164 行无目标队」是同一件事的两面（那 164 行里只有 29 人在平台上还有现队籍，其余本来就是自由身）。

⇒ 本批执行后，20 支队的**名单规模会涨**（合计估算 570 + 304 = 874，单队 31~56 人），因为遗留球员还挂在原队。若要严格按联盟世界收口名单，需要再开一批处理这 304 人（选项：`club_id = NULL` 释放 / 建布鲁日·国米·牛津联三队并安置 / 不动）。**这是待裁决项，本批不碰。**

## 6. 落库形状与守卫

```sql
UPDATE players SET club_id = 1, updated_at = '<生成时点>' WHERE fc_id = 277225 AND club_id IS NULL;
UPDATE players SET club_id = 66, updated_at = '<生成时点>' WHERE fc_id = 188545 AND club_id IS 241;
```

- 守卫用 SQLite 的 null 安全比较 `club_id IS <旧值>`（旧值为空时就是 `IS NULL`）⇒ 重放或错版落库时 `changes = 0`。
- 回滚分片用同一形状反向写（`WHERE fc_id = ? AND club_id IS <新值>`），写回**原样值**（NULL 就还 NULL）。
- `players.club_id` **没有外键**（`src/db/migrations/0001_init.sql:8` 只写 `club_id INTEGER`；有外键的是 `contracts`/`stadiums`/`club_bindings`）⇒ `--file` 分批执行不会踩 `PRAGMA defer_foreign_keys` 那条纪律（`scripts/README.md:66`）；单条命令逐个跑也可以，只是慢。
- 写入量：481 × 5（1 行 + 4 索引）≈ **2.4k rows_written**（免费档 10 万/天）。
