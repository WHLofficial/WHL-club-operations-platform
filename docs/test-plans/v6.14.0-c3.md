- 报价读侧：`listClubOffers` 口径（本队 pending@open + queued 常显）。

- 接班转正 `activateQueuedStatements`：批量转正、单队范围（退约触发）、跳过仍有 active 的队、快照入账、audit 与通知。

- 路由与权限：`/club/naming/quote`、`/club/naming/offers/:id/accept`、`/club/naming/terminate`、`/brands/market-round`、`/brands/market-round/reopen`、旧 `/club/naming/sign` 的 404 回归。
- 前端三处（TC-UI）：教练端冠名卡报价区、管理端招商轮面板、收件篮两条新模板渲染。

**Out of scope**

- 暗标/议价/24h 催签提醒（本版裁决不做）；品牌档位校准本体（v6.13.0 C2 域，回归覆盖即可）。
- 事件池其余事件与触发概率调参；球员转会市场 `/api/market/*`（§16，另一域）。
- 前端视觉/响应式细节：TC-UI 只验可达性、两态渲染、文案与错误透出。

## 最坏情况口径（铁律）

- 并发同刻两人抢同一份 offer：只有一方整批生效，输方 409 且零改行（抢锁 `AND status='pending'` + 后续语句全带守卫）。→ TC-ACCEPT-09
- 轮唯一 open：`uq_market_round_open` 部分唯一索引拦双开轮；清盘+开轮同批不冲突。→ TC-ROUND-03
- queued 部分唯一索引：`uq_market_offer_queued(club_id) WHERE status='queued'` 防同队双接班，且失败时零脏状态。→ TC-QUEUED-03
- 档位名额合并计数：active（按品牌名）+ queued（按 brand_id）合算；口碑/不限额档**不拼 quotaGuard**（bind 0 会让 `COUNT < 0` 恒假 → 永远签不上）。→ TC-OFFER-07 / TC-ACCEPT-12 / TC-ACCEPT-13 / TC-QUEUED-04
- TTL：签时 `expire_at < now` 顺手置 `expired` 再 409；`ttl=0` 走 `9999-12-31T00:00:00.000Z`（不设时限，关窗批清盘兜底）。→ TC-ACCEPT-04 / TC-OFFER-09
- 关窗批重放幂等（整批回滚）：市场三表与账本同批，任何一条失败整批回滚，不残留半轮。→ TC-ROUND-06
- 整轮无人签：品牌 heat −ignored（SQL 侧钳制，含 discarded 排除、有 accepted/queued 的品牌不扣）。→ TC-ROUND-07
- 品牌弃用（discarded）：开轮不出手、spawn 不候选；已递报价仍可签，但热度 +deal 被 `status='adopted'` 守卫拦下（不加冷却、也不报错）。→ TC-SPAWN-07 / TC-ACCEPT-15
- `requires_no_naming`：有生效冠名时事件在条件层被拦（不是靠效果落空）。→ TC-SPAWN-06
- `seededUnit`：事件选项抽取钉在 `[occurrenceId, choiceNo]` 上，同事件同选项可重放；offer_spawn 的随机源是 `env.rng`（可注入桩）。→ TC-SPAWN-05 / TC-SPAWN-10

## 用例

### TC-ROUND 轮生命周期（清盘 / 开轮 / 幂等）

**TC-ROUND-01 · 清盘：未签 pending 全作废，已签/接班保留，轮置 settled**（P0 · vitest）
- 前置：open 轮 R 含 pending×2、accepted×1、queued×1（accepted/queued 属两品牌）。
- 步骤：调 `buildRoundStatements(env, 1, 2)`，读 `market_offers` / `market_rounds`。
- 预期：两份 pending → `expired`；accepted/queued 原样；R.status='settled' 且 settled_at 非空；`hadOpenRound=true`；返回的 openStatements 指向新轮。

**TC-ROUND-02 · 无 open 轮：settle 段为空、照常开轮**（P0 · vitest）
- 前置：`market_rounds` 为空（或只有 settled 轮）。
- 步骤：`buildRoundStatements`。
- 预期：`settleStatements=[]`；`hadOpenRound=false`；openStatements 首条为新轮 INSERT；`offerCount > 0`（有可出手品牌）。

**TC-ROUND-03 · `uq_market_round_open` 防双 open（部分唯一索引）**（P0 · 变异验证）
- 前置：已有一条 open 轮。
- 步骤：直接 INSERT 第二条 `status='open'`；另跑一次 settle+open 批。
- 预期：直插报唯一约束失败，重读仍只有一条 open；合法批（先 settle 旧轮再开新轮）成功。
- 变异：删掉 `uq_market_round_open` 索引 → 本条红。

**TC-ROUND-04 · 新报价轮归属：`round_id` 绑定本批新轮**（P0 · vitest）
- 前置：旧轮 open 且有历史报价。
- 步骤：跑 settle+open 批并提交；读新报价的 `round_id`。
- 预期：所有新报价 `round_id` = 新轮 id（不是旧轮）；旧轮报价状态不变（除 pending→expired）。

**TC-ROUND-05 · 重开语义：连续两轮各自独立清盘**（P1 · vitest）
- 步骤：`buildRoundStatements` → 提交 → 再 `buildRoundStatements` → 提交。
- 预期：两轮均 settled + 一轮 open；第一轮 pending 全 expired；第二轮报价独立生成。

**TC-ROUND-06 · 关窗批整批原子：任一语句失败整批回滚（重放幂等）**（P0 · vitest）
- 前置：open 轮含 pending 报价；品牌 heat 可观测。
- 步骤：把 settle+open 语句与一条必败语句（如违反 CHECK）同批执行 → 捕获异常；重读三表。
- 预期：无 settled 轮、无新轮、pending 未变 expired、heat 未变、无新增报价 —— 即异常后重放可得同一最终状态。

**TC-ROUND-07 · 整轮无人签：heat −ignored + SQL 侧钳制**（P0 · vitest）
- 前置：open 轮内品牌 A（heat 1.0，仅 pending→expired）、B（heat 0.5，仅 pending）、C（heat 1.0，有 queued）；品牌 D（discarded）轮内有报价。
- 步骤：跑 settle 段（commit）后读 `brand_pool.heat`。
- 预期：A=0.97（+ignored=-0.03）；B=0.5（MAX 钳底不破）；C 不变（有 queued 视为「有人要」，不扣）；D 不变（`WHERE status='adopted'`）。

**TC-ROUND-08 · 批内顺序：settle 先于档位校准，open+转正在批尾**（P1 · vitest）
- 步骤：跑常规关窗批（`closeWindow` 路径），记录语句数组顺序；对同一环境跑临时窗。
- 预期：清盘语句索引 < 档位校准 < 收租/演化；开轮与接班转正在最后；临时窗（`chargeNaming=false`）无任何 market 语句。
- 备注：语句顺序是接线契约（插件 close→recalibrate→open 同序），改动会改变校准所见热度口径。

**TC-ROUND-09 · 临时窗全跳过**（P0 · vitest）
- 前置：临时窗（`chargeNaming=false`），存在 open 招商轮与 queued 报价。
- 步骤：跑关窗批。
- 预期：轮不 settle、报价不 expired、不开新轮、不转正；`summary.marketOffers/activatedClubs=0`；无 `naming_offer` / `naming_offer_activated` 通知。

### TC-OFFER 定向发放与挑队策略

**TC-OFFER-01 · 头部盯估值前 min(2, perBrand) 队**（P0 · 变异验证）
- 前置：头部品牌，`offersPerBrand=3`，6 队估值降序 [c1..c6]；另一环境 perBrand=1。
- 步骤：`pickTargetsForBrand('头部', 估值, 3, new Set())`；边界再跑 N=1、N=2。
- 预期：perBrand=3 → `[c1,c2]`（`Math.min(2,3)`，不是 3 队）；N=1 → `[c1]`；N=2 → `[c1,c2]`。
- 变异：改成 `slice(0, perBrand)` → 本条红（头部一次砸 3 队）。

**TC-OFFER-02 · 新兴盯中游窗口**（P1 · vitest）
- 前置：新兴品牌，估值降序 [c1..c6]，perBrand=3。
- 预期：`mid=floor(6/2)=3`、`start=max(0,2)=2` → `[c3,c4,c5]`；len=1 → `[c1]`；len=2 → `[c1,c2]`（slice 自然截断）。

**TC-OFFER-03 · 口碑广撒：未收价队优先、已收价队补位、轮内累积**（P0 · 变异验证）
- 前置：口碑品牌 X、Y，perBrand=2，队 c1 已收 X 报价（`offeredTeams={c1}`）。
- 步骤：先算 X 的 targets，`offeredTeams.add` 后算 Y 的 targets。
- 预期：X → `[c2,c3]`；Y → `[c1,c2]`（c1 转回零报价位、c2 已收价被排后）；最终 `market_offers` 无 `(round_id,brand_id,club_id)` 重复。
- 变异：去掉 zero/rest 分组排序，统一 slice → 本条红。

**TC-OFFER-04 · 空估值列表不炸**（P2 · vitest）
- 前置：品牌存在但无球场/无队（估值列表空）。
- 预期：targets=[]，不产生报价、不抛错。

**TC-OFFER-05 · 套餐按档位：头部进取 / 其余稳健**（P1 · vitest）
- 预期：头部 pkgNo=2（进取）、新兴与口碑 pkgNo=1（稳健）；`amount = 估值`、`windows` 取 `buildPackages(params, fee)[pkgNo-1]` 对应项；pkgName 一致。

**TC-OFFER-06 · `package_json` 快照：估值/套餐定死在报价上**（P0 · vitest）
- 前置：开轮后把品牌 heat 从快照时刻的 1.0 改成 1.4。
- 步骤：读报价 `package_json`，再签约。
- 预期：`{slot:'naming', pkgName, baseFee, bonusAmount, betAttend, betFans, brandHeat}` 全为开轮时刻值；合同 `base_fee = 快照 baseFee`（≠ 按 1.4 重算值）；brandHeat 快照也列化入合同。

**TC-OFFER-07 · 品牌侧名额过滤：active + queued 合并**（P0 · 变异验证）
- 前置：头部品牌 quota=1（已有 active → 不出手；另一品牌 active=0 但有 queued → 也不出手）；新兴品牌 quota=2 且 active=1 → 出手；口碑品牌无视名额。
- 预期：`buildRoundStatements` 只给未满品牌生成报价；名额按「品牌名 active 数 + brand_id queued 数」。
- 变异：只算 active 忽略 queued（或反之）→ 本条红。

**TC-OFFER-08 · 口碑（quota=null）恒出手**（P1 · vitest）
- 前置：口碑品牌已有 active 冠名。
- 预期：仍按口碑口径递价（不限额）；且不因「拼了错误的名额守卫」被静默跳过。

**TC-OFFER-09 · `expire_at`：ttl 语义**（P1 · vitest）
- 前置：`market_round_rules.offerTtlHours` 分别为 72 与 0。
- 预期：72 → `now + 72h`（ISO）；0 → `9999-12-31T00:00:00.000Z`。
- 变异：忽略 0 分支恒按 72h 算 → 本条红。

**TC-OFFER-10 · `listClubOffers` 口径：本队 pending@open + queued 常显**（P0 · vitest）
- 前置：c1 有 pending（轮 open）、pending（轮 settled）、accepted、expired、queued（跨轮）各一；c2 有 pending。
- 预期：c1 返回 = 轮 open 的 pending + queued（3 条）；settled 轮 pending、accepted、expired 不出现；c2 的报价不串入。

**TC-OFFER-11 · 全员收价：已有冠名的队照收报价**（P1 · vitest）
- 前置：c1 有 active 冠名（非本品牌）。
- 预期：c1 仍在估值池与 targets 内（本版裁决不排除有冠名队）；其报价走 TC-ACCEPT-07 的二选一流程。

### TC-ACCEPT 签约状态机

**TC-ACCEPT-01 · 无约 + 开窗 → signed 全链路**（P0 · vitest）
- 前置：offer pending（轮 open、未过期），队无 active 冠名，开窗中。
- 步骤：`acceptOffer(env, offerId, clubId, undefined, actor)`（或 `signViaOffer`）。
- 预期：offer → accepted；合同 active 且快照列化（base_fee/bonus/bet/pkg 号/windows）；品牌 heat `+deal` 且钳制；audit `naming_offer_accept`；返回 `{result:'signed', penalty:0}` 且 contract 非空。

**TC-ACCEPT-02 · 404 / 403 分支**（P0 · vitest）
- 预期：报价不存在 → 404「报价不存在」；报价属他队 → 403「这份报价不是递给你们队的」。

**TC-ACCEPT-03 · 状态门：expired / accepted / queued**（P0 · vitest）
- 预期：`status='expired'` → 409「报价已过期」；accepted 或 queued → 409「这份报价已处理过」；两情形均零改行。

**TC-ACCEPT-04 · TTL 惰性落态**（P0 · vitest）
- 前置：offer pending 但 `expire_at` 在过去。
- 步骤：`acceptOffer` 捕获 409 后重读 offer。
- 预期：409「报价已过有效期」；重读 status='expired'（顺手落态，不是只报错）。

**TC-ACCEPT-05 · 轮已关（round settled）**（P0 · vitest）
- 前置：offer pending、未过期，但所属轮 status='settled'。
- 预期：409「招商轮已关闭，签不了这份报价」；零改行。

**TC-ACCEPT-06 · 无约 + 无开窗**（P0 · vitest）
- 预期：409「转会窗口没开，签不了冠名合同」。

**TC-ACCEPT-07 · 有约时的 mode 二选一**（P0 · vitest）
- 前置：队已有 active 冠名。
- 预期：mode 缺省/非法值 → 400「已有生效冠名：签新报价请选择「到期后自动接替」或「解约当前并签新」」；零改行。

**TC-ACCEPT-08 · queued 分支**（P0 · vitest）
- 前置：有 active 冠名 + 开窗 + 名额未满的报价。
- 步骤：`acceptOffer(..., 'queued', ...)`。
- 预期：offer → queued；不产生第二份合同；audit 落库（含 queued 语义）；返回 `{result:'queued', contract:null, penalty:0}`；`uq_market_offer_queued` 被占用后同队第二份 queued 走 TC-QUEUED-03。

**TC-ACCEPT-09 · 并发同刻双签：只有一方整批生效**（P0 · 变异验证）
- 前置：offer pending。
- 步骤与断言（三层）：
  1. 文本锁：signed 批首 UPDATE 带 `AND status = 'pending'`；合同 INSERT 带 offer='accepted' 与 `NOT EXISTS (active)`；audit `guardSql` = offer 状态为 accepted。
  2. 抢赢：正常签约成功（合同 1 份、heat 只加一次、无双账本）。
  3. 抢输：手工把 offer 置 accepted（模拟对方已提交），再 `acceptOffer` → 409（状态门），且 `market_offers`/`naming_contracts`/`brand_pool`/`ledger` 与调用前完全一致。
- 变异：删掉抢锁的 `AND status = 'pending'` → 第 1 层红。

**TC-ACCEPT-10 · terminate 全链路：解约赔款 + 换签**（P0 · vitest）
- 前置：active 合同（windows_remaining=3、fee_per_window=10）、新 offer。
- 预期：旧约 status='terminated' + ended_season/window；`penalty=round3(max(0,3-1)×10×terminatePenalty)`；账本 −penalty（kind `naming_penalty`，refId=旧约，guardSql 旧约='terminated'）；新约 active；品牌 heat +deal；返回 `{result:'terminated', penalty>0}`。

**TC-ACCEPT-11 · 零赔款边界**（P1 · vitest）
- 前置：windows_remaining=1。
- 预期：remaining=0 → penalty=0 → 无赔款账本语句；换签仍成功。

**TC-ACCEPT-12 · 名额预检 409 文案**（P0 · vitest）
- 前置：头部品牌 active=1（quota=1）；新兴品牌 active=1 + queued=1（quota=2）。
- 预期：409「品牌「X」档位名额已满（头部/新兴档限 1/2 队）」，零改行。

**TC-ACCEPT-13 · quotaGuard 文本锁 + 口碑 bind 0 陷阱**（P0 · 变异验证）
- 断言：quota 非 null 时，合同 INSERT 与 queued UPDATE 均带 `(SELECT COUNT(*) FROM naming_contracts WHERE brand=(SELECT brand FROM brand_pool WHERE id=?) AND status='active') + (SELECT COUNT(*) FROM market_offers WHERE brand_id=? AND status='queued') < ?`；quota===null（口碑）时**不带**该片段。
- 行为：口碑品牌同队多份签约均成功（证明守卫未误拼）。
- 变异：让 quota=null 也拼 guard 并 bind 0 → 本条红（口碑路径恒 409）。

**TC-ACCEPT-14 · terminate 竞态：别批抢先解约不重复赔款**（P1 · vitest）
- 前置：active 合同 C + 新 offer；先把 C 直接置 terminated（模拟另一批解约已完成理赔）。
- 步骤：`acceptOffer(..., 'terminate', ...)`。
- 预期：新约落库成功；`ledger` 不出现第二条 `naming_penalty`（解约赔款唯一）；若首跑出现双赔款 → 本条红，列入风险表待修。
- 备注：terminate UPDATE 带 `AND status='active'`，天然防止一份旧约被两次置 terminated；赔款唯一性依赖账本 guardSql。

**TC-ACCEPT-15 · 弃用品牌仍可签、热度不再加**（P1 · vitest）
- 前置：报价品牌在递价后被置 discarded；offer 仍 pending。
- 预期：签约成功（合同照落、无报错）；品牌 heat 不变（`status='adopted'` 守卫拦下 +deal，不产生冷却）；audit/合同与正常一致。

**TC-ACCEPT-16 · 合同落库后读不回 → 500 兜底**（P3 · 人工/注入）
- 步骤：在合同 INSERT 与读回之间注入破坏（测试桩/手工改库）。
- 预期：500「冠名合同落库后读不回来」；不返回半成品 contract。
- 备注：常规夹具难构造，标人工；生产监控以 5xx 计数兜底。

### TC-QUEUED 接班转正

### 4. 失败详情与后续动作

1. **实现缺陷 A（本轮实测发现，已于同日修复）**
   - 位置：`src/worker/market-ops.ts` 的 `activateQueuedStatements`（接班转正批）。
   - 机制（修复前）：每队三条语句按「①合同 INSERT → ②`UPDATE market_offers SET status='accepted' WHERE id = ? AND status='queued' AND NOT EXISTS (SELECT 1 FROM naming_contracts WHERE club_id = ? AND status='active')` → ③`naming_activated` 审计（守卫 offer status='accepted'）」入批；同批内 ① 先落 ⇒ ② 的 `NOT EXISTS(active)` 立即为假 ⇒ ② 0 改行、③ 守卫不成立。
   - 表现（修复前）：转正合同照落（用户可见的「接班转正」结果正常），但报价永停 `queued`、`naming_activated` 审计不落、`uq_market_offer_queued`（一队一接班位）永不释放 ⇒ 同一队此后排不进第二个接班位；管理端流水该报价长期显示 queued。
   - **修复（2026-09-29，随本测试轮落地）**：批内顺序改为「② offer UPDATE（占坑）在前 → ① 合同 INSERT（守卫 `offer='accepted'` + `NOT EXISTS active`）→ ③ 审计」；并发防线不变（② 的 `NOT EXISTS(active)` 挡跨批竞态，① 的双重守卫挡重复落约）。TC-QUEUED-01/04/05、TC-ROUTE-06 断言已同步改回正确行为，TC-QUEUED-07 的源码文本锁更新为 `offer='accepted'` 守卫。修复后全量 vitest 60 文件 / 1060 例全绿。
