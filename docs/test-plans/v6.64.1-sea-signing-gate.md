# v6.64.1 测试计划 · 海捞资格链补「在签约谈判」一关

> 判级 **patch**（零迁移、零新端点、零契约变更；只是把已有守卫链补一格，向后兼容）。
> 需求真源：owner 口述（2026-10-31）「海捞已经进入签约谈判的球员，应当阻止教练提出海捞申请，海捞资格查询也应该是无法海捞」。
> 关联口径：规则 4.4.4（海捞只能签无归属球员）、规则 4.4.3（海捞费 = 新违约金 × 30%）；v6.50.0 暗标与明标共用同一条资格链。

## 1. 需求真源（锁定口径）

| # | 口径 | 出处 |
| --- | --- | --- |
| 1 | 单据审核通过后进 `signing`（签约谈判），此时球员还没过户、`players.club_id` 仍为空，因此归属于「无归属球员」——旧 `findInFlight` 只认 `pending_review`，挡不住第二张单 | 本版根因 |
| 2 | 判定点在 `checkSeaSignEligible`（`src/worker/bypass.ts`）——`createFreeAgent` / 暗标 `submitSealedBid` / 开标重判共用它，改一处即全覆盖 | 既有结构（v6.17.0 起） |
| 3 | 拦截文案与状态码：`stage='signing'`、400、`errCode='sea_signing'`、文案「这名球员的海捞单已经进入签约谈判，等它成约或作废再操作」 | 本版裁决 |
| 4 | 守卫顺序不得调整：`window → ownership → status → banned → listing → pending → signing`，新关排在 pending 之后（用户看到的第一个红灯不能变） | 既有注释约定 |
| 5 | `GET /market/sea-lookup` 的批量快照副本必须逐字同口径（一条 `status IN ('pending_review','signing')` 查询，按状态分两个集合），否则情报台与详情页会互相打脸 | 既有约定（tests 有跨实现一致性用例） |
| 6 | 已结束的单据（`rejected` / `completed`）不构成在途，不得误伤 | 本版边界 |
| 7 | 成约（`completed`）后归属落位，后续由 ownership 关拦截（文案不同），不是本关的职责 | 既有口径 |

## 2. 测试范围

**In**：`checkSeaSignEligible` 新增关的判定与文案；明标提交（`POST /api/transfers/free-agent`）与暗标提交（`POST /api/transfers/sea-sealed`）两条入口的拦截效果；`GET /market/sea-lookup` 快照副本一致性；已作废单据不误伤。

**Out**：开标重判走同一函数（`openSeaBatch`），本版未单独造批次级用例——函数级行为已由明标/暗标两条入口锁住；`GET /api/players/:id` 的 `seaSign` 字段形状不变（矩阵用例顺带校验）；前端文案（本次零前端改动，球员页/情报台直接显示服务端 `reason`）。
