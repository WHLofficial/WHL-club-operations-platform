> **增量范围判级**：**patch**（缺陷修补 —— 库里中文队名 vs 截图英文队名必然对不上，识别结果被 400 拦下）。动因：用户报 4 张图全失败「截图队名「FIORENTINA」/「CHELSEA」对不上这场比赛（切尔西 vs 佛罗伦萨）」，并指明「卡在中英对应了」。落点：`src/worker/routes/admin/growth.ts`（提示词与队名对侧）、`src/core/growth-ocr.ts`（新增队名比对纯函数）、`tests/growth-ocr.test.ts`、`tests/growth-ocr-endpoint.test.ts`。**零迁移、零生产写、前端零改动**（识别链全只读）。

## 范围与风险

**In**：
1. `OCR_PROMPT` 要求 `team` 字段输出**中文队名**：JSON 示例值改 `"team": "切尔西"`，并给一条映射示例（CHELSEA → 切尔西、FIORENTINA → 佛罗伦萨、FC BAYERN MÜNCHEN → 拜仁慕尼黑、RB LEIPZIG → RB莱比锡、REAL BETIS → 皇家贝蒂斯）；没有通行中文译名时才照抄截图原文。
2. `src/core/growth-ocr.ts` 新增队名对侧纯函数：`teamNameKey`（折叠大小写/变音符 → 去空格标点 → 反复剥首尾俱乐部前后缀 `rb/fc/ac/cf/sc/afc/cd/sv/sk/fk/bk/tsv/club/cpu`）、`isSameTeamName`（先归一化逐字/互相包含，再比核心名；核心 <2 字符只认相等）、`matchOcrTeamSide`（先主后客；队名缺失或对不上回 null）。
3. 端点改用 `matchOcrTeamSide`；**400 文案不变**（模型不听话给英文名时仍是同一条 400，护栏不退让）。

**Out**：不落「英文名 → 中文名」映射表（`web/assets/ref/team.json` 696 项 + `clubs.id` 落游戏真号本可搭桥）；不改 `max_tokens`（v6.51.2 已修）；不动 `resolveEntrySide` 与花名册认人（球员名与截图同源，无需桥接）。

**最坏情况口径**：
- 模型不按提示词给中文名（返回英文）⇒ 仍是同一条 400 与既有文案，用户看到的行为**与 v6.51.2 相同**，不会更差。英文兜底属有意取舍：条件式指令已被实测否决，硬编码 20 队英文名会多出一份真名漂移源。
- 译名漂移超出现有容忍（如「慕尼黑1860」被写成「TSV 1860慕尼黑」）⇒ 仍 400 点名，交人工确认，不猜。
- 提示词改动连带把球员名中文化 ⇒ 认人失配（花名册 official 名是 FC26 缩写）—— **已实测排除**（4/4 图球员名保持英文缩写）。
- 核心名剥离过度造成误判 ⇒ 只在同场两队（2 个候选）内判定且 `home` 优先，风险局限在「同场两队核心名互相包含」的极端巧合。

- **已否决变体（探针历史）**：把本场两个候选中文名写进提示词让模型二选一 → **0/4 生效**（模型照抄英文原文）；追加式同义指令 → 4/4 生效。结论：这档小模型只吃「直接指令 + 映射示例」，不吃条件式规则。
