# v6.51.3 · 截图识别的队名对侧：模型改输出中文队名 + 译名/前后缀漂移容忍 + 同城同前缀歧义保护（测试计划）

> **增量范围判级**：**patch**（缺陷修补 —— 库里中文队名 vs 截图英文队名必然对不上，识别结果被 400 拦下）。动因：用户报 4 张图全失败「截图队名「FIORENTINA」/「CHELSEA」对不上这场比赛（切尔西 vs 佛罗伦萨）」，并指明「卡在中英对应了」；追加要求「兜底要考虑，万一以后有国际米兰怎么办，就像现在有拜仁慕尼黑和慕尼黑1860一样」⇒ 本轮加**歧义保护**。落点：`src/worker/routes/admin/growth.ts`（提示词与队名对侧）、`src/core/growth-ocr.ts`（新增队名比对纯函数）、`tests/growth-ocr.test.ts`、`tests/growth-ocr-endpoint.test.ts`。**零迁移、零生产写、前端零改动**（识别链全只读）。

## 范围与风险

**In**：
1. `OCR_PROMPT` 要求 `team` 字段输出**中文队名**：JSON 示例值改 `"team": "切尔西"`，并给一条映射示例（CHELSEA → 切尔西、FIORENTINA → 佛罗伦萨、FC BAYERN MÜNCHEN → 拜仁慕尼黑、RB LEIPZIG → RB莱比锡、REAL BETIS → 皇家贝蒂斯）；没有通行中文译名时才照抄截图原文。
2. `src/core/growth-ocr.ts` 新增队名对侧纯函数：`teamNameKey`（折叠大小写/变音符 → 去空格标点 → 反复剥首尾俱乐部前后缀 `rb/fc/ac/cf/sc/afc/cd/sv/sk/fk/bk/tsv/club/cpu`）、`teamNameMatchStrength`（**强度分层**：3 归一化逐字 / 2 核心名相等 / 1 归一化或核心名互相包含，包含判定要求 ≥2 字）、`isSameTeamName`、`matchOcrTeamSide`（强度高者胜出；**两侧同强度回 `'ambiguous'`**；队名缺失或都不像回 null）。
3. 端点改用 `matchOcrTeamSide`：对不上仍是原 400 文案（模型不听话给英文名时同一条 400，护栏不退让）；歧义另给 400「截图队名「X」这场两侧都像（A vs B），分不清主客——请换一张队名更完整的截图，或手动选边」。用户侧表现 = 该张图不出预填、识别报告区红字一行，手填与主/客切换不受影响。

**Out**：不落「英文名 → 中文名」映射表（`web/assets/ref/team.json` 696 项 + `clubs.id` 落游戏真号本可搭桥）；不改 `max_tokens`（v6.51.2 已修）；不动 `resolveEntrySide` 与花名册认人（球员名与截图同源，无需桥接）。

**最坏情况口径**：
- 模型不按提示词给中文名（返回英文）⇒ 仍是同一条 400 与既有文案，用户看到的行为**与 v6.51.2 相同**，不会更差。英文兜底属有意取舍：条件式指令已被实测否决，硬编码 20 队英文名会多出一份真名漂移源。
- 译名漂移超出现有容忍（如「慕尼黑1860」被写成「TSV 1860慕尼黑」）⇒ 仍 400 点名，交人工确认，不猜。
- 提示词改动连带把球员名中文化 ⇒ 认人失配（花名册 official 名是 FC26 缩写）—— **已实测排除**（4/4 图球员名保持英文缩写）。
- 核心名剥离过度造成误判 ⇒ 由**强度分层**兜住：只有两侧强度相同才叫歧义（不猜），强度不同必取高者；且只在同场两队（2 个候选）内判定，「曼」这类单字因 <2 字直接不判包含。
- 同城同前缀的两支队（拜仁慕尼黑 / 慕尼黑1860，未来的国际米兰 / AC米兰）⇒ 只写片段（「慕尼黑」「皇家」）两侧同强度 → 400 报「分不清主客」，用户手填；写全了强度高者胜。

Onana` / `João Pedro` / `H. Vanaken` …）；`finish_reason=stop`、JSON 可解析、rows 12；耗时 15.1 / 16.3 / 14.6 / 12.1 s，usage in=3572、out=654 / 649 / 681 / 561；提示词 1555 → 1686 字符。
- **已否决变体（探针历史）**：把本场两个候选中文名写进提示词让模型二选一 → **0/4 生效**（模型照抄英文原文）；追加式同义指令 → 4/4 生效。结论：这档小模型只吃「直接指令 + 映射示例」，不吃条件式规则。
- **复测（歧义保护落地后同口径重跑 4 张图）**：**4/4 仍 HTTP 200 且队名全中**（`PROBE_ALL=1`）；耗时 **15.8 / 14.1 / 15.3 / 15.2 s（平均 15.1 s，无重试）**，出参 654 / 651 / 681 / 645 tokens（占 `max_tokens 1024` 上限 **63–67 %**，12 行场景留约 1/3 余量 ⇒ 不触截断），`finish_reason` 全 `stop`，`reasoning` 0 字符（无额外思考文本）。**质量抽查（门将页全文 JSON）**：`tab=goalkeeping` 页签识别正确、9 名首发 + 3 个 SUB（`rating: null`，提示词规则被遵守）、门将自检 `saves 1 + goalsConceded 2 = shotsOnTarget 3` 成立、`selected: null`（非 Summary 页不填）、评分为 JSON number（`7.4` / `6` 这类不写成字符串）、队名 `佛罗伦萨` 与库内一致、球员名仍为英文缩写（`M. ## 登记

**未验证项**：① 生产管理端真机各跑一次识别（探针走的是同模型同提示词，未过端点完整链路：D1 花名册、落侧后的草稿预填）；② 漂移容忍只覆盖生产 20 队名与常见译名，未做 696 队穷举；③ 歧义分支只在单测里构造（真图 4/4 都给全名，未触发 `'ambiguous'`，故「用户看到 400 后手动选边/手填」这条路径待真机出现时观察）。

**口径**：① 「示例值即中文」是这档小模型的格式锁（弱指令跟随 ⇒ 示例比规则有效）；② 提示词只约束 `team` 字段，球员名保持截图原文缩写（认人靠它）；③ 英文兜底表有意不做，模型不听话时的 400 与 v6.51.2 行为一致；④ 队名对侧先判相等（逐字 / 核心名）再判包含，强度高者胜 —— 同城同前缀的队只在「只写片段」时才同强度，此时报 400 让用户手填，不替用户猜（默认主队会静默把花名册认到错的一侧）。
