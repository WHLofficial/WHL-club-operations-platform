## 9. 风险与最坏情况

- **「类型层零风险」是错觉**：A 类处置把 api.ts 的谎言改成现实，typecheck 会**当场暴露一批潜伏前端缺陷**（transfer-board ca/pa null、attrValue null、settled.wage null、offer.season null、MyClubOverview.home 缺键）。最坏情况 = 某读点没有 `?? fallback` 直接 `toFixed()`/算术——编译期即红，按 R-WEB 补防线即可；**但绝不许为保 typecheck 绿而把契约类型写回谎言**（那等于本轮白做，且 TC-LOCK-08 会拦）。
- **§6.8 补录 9 类型未经逐字段甄别**：worker 真源行已核证、初始处置已给，但 fieldDiff 对拍缺位——最坏情况 = 落地时冒出未预期 diff（如 M0Report 某字段 worker 可空而 api 非空）。处置规则已写死（§6.8 前注：随批补甄别、发现 diff 照 A–G 挂处置并补 LOCK-08 行），不许因「计划没写」而静默照抄 api 手抄。
- **web 零改动线可能被 R-WEB 打折**：A 类防线补丁改动的是 web **运行时**文件（非测试文件）。「既有 vitest 用例零改动」不受影响（防线不改变已渲染输出），但「web 运行时零改动」的口径要如实缩窄为「除 §6 处置表点名条目外零改动」，交付说明逐条列出。
- **B5 死分支删除是唯一有产品语义的动作**：证据链完整（worker 响应无此字段 → 分支恒假 → 从未渲染），TC-B5-01 锁删除前后可见输出一致。若评审认定「本应让 worker 补发 freeRcChange 让免费提示亮出来」——那是行为增量，**另立增量**，本轮不做（运行时零变化铁律）。
- **契约 barrel 单点**：index.ts barrel 是 LOCK-01/对账的机器清单，barrel 漏导出某类型 → api.ts re-export 缺名 → web typecheck 红（消费方 import 失败），双保险成立；但「契约有而无人 import」的死类型不会红——对账步骤 6 人工点名兜底。
- **跨批单源破坏**：MatchEntry*/Import* 等若被两批各建一份（图省事不归源），TC-LOCK-05 的全 web 扫描不拦（worker 侧两份契约文件互相独立）——靠 §6.0 归属表 + 评审透镜「无双真源」兜底；LOCK-02 的「来源限本目录与 core」会把 B4 引用 B2 契约文件的跨目录 import 暴露为 `from './players/…'` 形态（ barrel 内部相对引用合法，不误伤）。
- **文本锁的脆弱性**：LOCK-07/08 锁的是源码字面量，重排字段行会误红——断言用「标识符 + 类型片段」正则而非整行精确匹配，实现时按此口径写，避免把计划变成不可维护的格式锁。
- **并行会话风险**：六批涉及 worker 文件 30+，动手前后 `git status --porcelain` 逐文件复查；脏文件跳过登记 deferred，绝不 stash/checkout/restore。
