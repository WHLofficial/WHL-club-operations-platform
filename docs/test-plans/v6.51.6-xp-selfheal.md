# v6.51.6 测试计划 · 赛事侧成长数据自动补账（没解析到的场次由 cron 重放钩子补齐）

> 判级 **patch**（同一链的自愈补丁，无新端点、无页面）。
> 动因：用户报「发现生产库有一些应当从赛事侧自动生成的成长数据没有生成」，口径三次修订后定为「**算了，还是自动重试吧**」。
> 落点：`src/worker/results.ts`（新增 `retryUnresolvedResults`）、`src/worker/index.ts`（`runSettleTick` 接线 + `tickChanged` 条件）、`tests/results.test.ts`、`TECH_DESIGN.md:978`。
> **零迁移、零新端点、零前端改动** ⇒ 上线只需 push；部署后由既有 cron（`*/5 * * * *`）按跳收敛，也可 `POST /api/cron/tick` 立即触发一跳。

## 范围与风险

**In**
- cron 每跳扫「没解析到」类标记的场次（`needs_review = 1 AND review_note LIKE '%没解析到%'`），逐场重放确认钩子。
- 通了清标记；没通记「（自动重试 N 次）」，第 3 次起写「自动重试已放弃」不再占额度。
- 每跳上限 `cap = 20` 场（56 场欠账 ≈ 3 跳收敛）。
- `tickChanged` 增 `xpRetry.healed > 0`：只有真补到账的跳才 purge 公开缓存（补账写 `players.growth_xp`，公开球员载荷可见）。

**Out（有意不做）**
- 不做一次性补数脚本（用户先提后撤）。
- 不自动重试「通知发送失败」「奖金入账失败」「XP 事件入账失败」等其它标记——重放对通知没有补偿能力，清了标记反而掩盖。
- 不在重放里补发通知（`replayHooksForMatch` 内部 `notify: false`，与既有管理端重放一致）。
- 不改确认链路本身（不把钩子挪进确认批次、不做待办队列）——本版只做「欠账自愈」。

**最坏情况口径**
| 场景 | 结果 |
| --- | --- |
| 重放仍然解析不到（数据真缺） | 标记保留并计数，3 次后写「已放弃」、不再占每跳额度；人工修完数据仍可从管理端 `POST /api/admin/results/:id/replay-hooks` 手点重放 |
| 重放本身抛异常（单场） | 只 `console.warn('[xp-retry] 重放 #N 失败：…')`，本跳继续处理其余场次（不整跳失败） |
| 重复重放同一场（cron 撞管理端手点） | 三账都不双记（见「口径 ①」），最坏是多跑一次钩子 |
| 补账把 `growth_xp` 改动但公开缓存没清 | `tickChanged` 已把 `xpRetry.healed > 0` 计入 ⇒ 真补到账必 purge；`healed = 0` 的跳不 purge（稳态零成本） |
| 场次多到 `cap` 用满 | 每跳按 `match_id` 升序取前 20，剩余留到下一跳；不会漏（标记未清就仍被扫到） |

## 登记

**未验证项**
1. 生产收敛速率（56 场 / cap 20 每跳 ⇒ 预期 3 跳内）与最终 `needs_review` 归零——只有上线后查库才能验。
2. 补出的 auto 事件数是否等于 170 goal / 140 assist（assist 依赖 `assist_player_id`，若赛事侧个别事件缺助攻者，缺口会略小于此数）。
3. `match_ref = '33'` 的自动入账与用户手录 85 条并存后的 `growth_xp` 值（手录评分/对抗等与自动球助是否在同一球员上重叠）。
4. 第 3 次上限之外的长尾（若生产存在 4 次以上才通的场次）——本版不覆盖。

**口径**
1. 重放幂等是三账各自的既有锚：XP 靠 `growth_events` 的 `UNIQUE(player_id, match_ref, event_type)` + `players.growth_xp` 增量的 `NOT EXISTS` 闸（`src/worker/growth.ts:140-157`）；奖金走 `ledgerMovement` 的 `(club_id, kind, ref_type, ref_id)` 默认幂等闸（`src/worker/ledger.ts:29`）；比赛日收入按 `match_attendance` 主键早退（`src/worker/home.ts:330`）；通知钩子重放直接跳过。**只要这些锚还在，重复重放就安全**。
2. 只自动处理「没解析到」：这类标记的成因是数据/关联问题，重放能修；通知类不行（重放无补发能力）。
3. 上限取 3 次：连续 3 跳（15 分钟）仍解不开的多半是真缺数据，继续重试只是占额度并刷 note；放弃后不隐藏问题（note 写明「已放弃」+ 人工路径）。
4. `cap = 20` 与 `autoConfirmResults` 的既有上限一致，避免单跳把子请求预算用光。
5. `tickChanged` 只在 `healed > 0` 时 purge：`growthXp` 在公开球员载荷里，补账后必须清；无补账的跳不付这次 KV 写。
