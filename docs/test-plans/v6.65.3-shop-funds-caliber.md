# 测试计划 · v6.65.3 消费中心资金口径统一（现金 → 可支配 + 券）

## 背景与范围

RB 莱比锡报「消费中心徽章提交没反应」。查证坐实口径分裂：消费域（六个商品类 + 球场扩建/升级）资金守卫只看裸现金余额，转会域全线用 `availableBalance` = 余额 − 现行冻结 + 在途收入额度；且失败反馈只有一条 3 秒 toast（工单落库即删、券参与时审计连带跳过）。本版把消费域守卫统一到可支配口径（先券后钱不变）、失败文案带差额、顶部余额条改拆解、冠名退约确认弹窗亮赔款。

**In scope**：`createClubOrder` 预检 + 批内守卫、`payAndRefund` 预检 + 扩建/升级批内守卫、`/api/me/club` funds 字段、`/api/club/naming/quote` terminatePenalty、ShopPage 余额条与五卡确认弹窗、venueCards 退约/换约确认弹窗。
**Out of scope**：工单 `failed` 状态留痕（远期）、冠名退约加资金守卫（裁决维持可透支）、审核/退款路径（不动钱）、e2e（环境阻塞沿用组件测试兜底）。

## 用例

### 后端 · 消费工单（tests/shop-orders.test.ts）

- **TC-F-01 (P0) 授信覆盖可买**：现金 2m、无券、挂一张有活跃出价的在途挂牌（净收入额度 ≥ 差额）→ 提交 4m 徽章单成功；余额扣成负数；ledger/audit 各 1 行。
- **TC-F-02 (P0) 冻结挤占可支配**：现金 10m、held 8m（现行冻结）、无授信 → 提交 4m 单 → 400，文案含「可支配」与具体金额；**无工单行落库**（预检拦截，不再落单+删单）。
- **TC-F-03 (P0) 授信也不足**：现金 0.35m、券 0.45m、无授信 → 提交 12m 角色单 → 400 文案带「券抵 0.45」「还需现金」数字。
- **TC-F-04 (P1) 先券后钱不变**：券 5m、现金 0、可支配 0 → 提交 4m 单 → 全券抵扣成功、现金流水 0 距（cash=0 不落账本）、余额不动。
- **TC-F-05 (P2) 边界：可支配为负 + 纯券单**：现金 −5m（授信消费后）、券 5m、cash=0 → 拒（与现状「负余额拒纯券单」方向一致）。
- **TC-F-06 (P1) 失败无痕复核**：TC-F-02/03 拒绝后 `shop_orders` / `audit_log` 均无新增行。

### 后端 · 球场域（tests/stadium-ops.test.ts）

- **TC-S-01 (P0) 授信覆盖扩建**：现金 2m、在途额度 10m → 扩建费用 8m 成功；余额 −6m。
- **TC-S-02 (P0) 冻结挤占 → 400**：held 吃掉可支配 → 400 文案含「可支配」数字，扩建/券/余额原样。
- **TC-S-03 (P0) 批内竞态链不断**：预检后券被并发扣空 → 首句守卫（券检查保留）整批空转，座位/券/现金/流水/审计都不动（现有 TC-B-002 同款，补授信维度：券足 + 现金靠授信 → 正常落库）。
- **TC-S-04 (P2) 升级共用 payAndRefund 同口径**（扩建已覆盖公式，升级一条冒烟）。

### 后端 · 冠名赔款预览（tests/market-rounds.test.ts TC-ROUTE-01 扩展）

- **TC-N-01 (P2)**：GET /api/club/naming/quote 有约分支多下发 `terminatePenalty`（= max(0, 剩余窗−1) × 每窗费 × 30%，round3）；无约分支不出该键。

### 前端（web/src/pages/shop/ShopPage.test.tsx）

- **TC-W-01 (P1) 拆解条**：funds 下发时顶部显示「可支配 X m（现金 Y · 券 Z）」。
- **TC-W-02 (P2) 缺省回落**：无 funds 字段时保持「资金余额」旧行径（兼容半旧响应）。
- **TC-W-03 (P1) 确认弹窗券抵**：voucherBalance > 0 时徽章确认文案含「券抵 X，实付 Y」；券 0 时不含。
- **TC-W-04 (P2) 退约/换约确认亮赔款**：venueCards 退约确认含「赔金 X m」或「无赔金」——若 NamingCard 渲染基建成本过高则列手工验收并在此标注。

## 最坏情况口径备注

- 批内守卫是 SQL 内嵌公式：变异 M2/M5 验证「漏掉一项就红」，另需确认 `creditLineGuard` 参数个数按占位符重复绑定（漏绑静默落 NULL 的坑在测试里以「授信刚好够」的等值用例钉住——TC-F-01 取恰好等值边界）。
- 预检与批内守卫必须同公式：TC-F-01 的授信恰好够场景同时过预检与批内守卫，防止「预检按可支配、批内按现金」的回归（bypass.ts:175 同教训）。
