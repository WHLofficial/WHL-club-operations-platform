## A 组 · deadline_note 批量化（真凶修复）

### TC-NOTE-01 常态零逐行写（语句数锁）
- **优先级**：P0｜**类型**：性能 + 行为
- **前置**：本地 D1 夹具，N 张在售挂牌（listed+bidding 混合，≥3 张），note 均无需变更
- **步骤**：用计数代理包 `env.DB.prepare`（按 SQL 含 `UPDATE listings SET deadline_note` 过滤），跑一次 `settleOverdue(env, { origin:'user' })`
- **预期**：该类 prepare 调用 ≤ 1（0 或 1 次 batch 内语句），`deadline_note` 值全部正确；代理对逐行循环的变异（拆回 per-row `await .run()`）**恰红**
- **变异**：把批量化拆回逐行循环 → TC-NOTE-01 恰红（确认红的是语句数断言本身）

### TC-NOTE-02 只写变更行
- **优先级**：P0｜**类型**：行为
- **前置**：两张在售单，一张 note 会变（把 `deadline_hours` config 改到跨天或直接构造 `deadline_note` 为旧文案），一张不变
- **步骤**：跑结算后读两行 `deadline_note`
- **预期**：变更行更新为新文案且 `summary.notesUpdated=1`，未变更行原值不动（`changes=0` 路径不产生写）

### TC-NOTE-03 结算语义回归
- **优先级**：P0｜**类型**：回归
- **预期**：现有 market-rounds / market-activatable 套件全绿——窗尾收口、到期下架收费、匹配窗到期成约、note 文本口径（`noteText`）全部原样；批内每条 UPDATE 保留 `AND status IN ('listed','bidding')` 写闸
- **风险留痕**：batch 是隐式事务，部分失败全回滚——与逐行版「部分成功」不同；note 更新幂等可重放，可接受，ROADMAP 登记

## 最坏情况口径（按仓库铁律）

- 变异按将来最可能的重构方式弄坏：note 批量化拆回逐行（最自然的「简化」）、ctx 合一拆回单键、聚合拆回两条分查——各自确认**红的正是对应语句数断言**，不是连带红。
- 语句数锁对源码格式不敏感（不用源码文本 `toContain`，全部走运行时代理计数，天然免疫 CRLF）。
- 边界：N=0 张在售单（batch 空数组不发送）、note 恰好跨天变化、bids 为空表的聚合子查询、settle 在 waitUntil 中抛错不致 unhandled rejection。
