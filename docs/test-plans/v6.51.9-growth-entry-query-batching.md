## 范围与风险

**In**
- **A 列表端点**：主查询与 `SELECT id, name FROM clubs` 并发取（`Promise.all`），队名 → 俱乐部归属改**内存查表**（`clubIdMapOf` / `entrySideOf`，口径与 `resolveEntrySide` 一致）；赛事名仍单独一趟（跨库，要等主查询拿到 `tournament_id`）。往返 约 22 趟 → **3 条 / 2 波**，且与场次/队数无关。
- **B 面板端点**：原八段串行（场次行 → 两队归属 → 赛事名 → 停赛复算 → 已录事件 → 主花名册 → 客花名册 → 累计基数，线上实测约 17 趟）并成**三波**——① 场次行 ∥ clubs 全表 ∥ 已录事件 ∥ 停赛复算 ② 赛事名 ∥ 两侧花名册（一次 `DB.batch`）③ 累计基数（依赖花名册 id）。本库 6 条 + 赛事库 8 条。
- **C 停赛复算去重**：`loadTeamDiscipline` 不再自己查「本队有哪些 entry」（调用方已持有本场两侧 entry，直接传 `entryIds`），且「比赛序 ∥ 红黄牌事件」并发；`suspendedPlayersAtMatch` 的「配置 ∥ 两侧 entry」并发、两侧队伍的数据并发取。查询 9 → **7** 条。
- 保留 `resolveEntrySide`（单场调用方：OCR 端点、批量端点），列表/面板改走内存表版。

**Out（有意不做）**
- D 新索引 `growth_events(match_ref)`：面板「已录事件」一趟本身不慢，本版不动。
- E 列表悬停预取：先看 A/B/C 的实际体感，不做前端行为改动（本版零前端改动）。

**最坏情况口径**
| 场景 | 结果 |
| --- | --- |
| clubs 表变大（远期） | 全表取回是按行数线性的；仍远小于「每场两次单行查询」，且 20 行级常态下可忽略（本版按现状取舍，见「口径 2」） |
| 队名在 clubs 里查不到（未建档队/改名漂移） | `entrySideOf` 留 `clubId = null`，与 `resolveEntrySide` 同口径——前端照旧按「无归属」处理 |
| CPU 侧的 `bind(-1)` 行为 | `club_id = -1` 走索引空集，返回零行；等价于原来「不查」；语句位置恒定 ⇒ 结果按 `[主, 客]` 下标对齐 |
| 并发度触到单请求子请求上限 | 本库同时 4 条、赛事库同时 2 条（停赛内部），远低于 Workers 上限；无新连接池语义（D1 走同一 binding） |
| 停赛复算改为「只传本场这一支 entry」改变判定 | 不改变：本队别的 entry 的序列只对「事件记在别的 entry 上」的球员有用，那类球员本场 `seq.findIndex(m.id === matchId)` 恒为 -1，原实现同样整人跳过（TC-SUS-15 钉死） |

## 登记

**未验证项**
1. 真机体感（管理端列表与面板的实际打开时间）——本版只按「往返次数」量化，未做真机计时 ⇒ 用户侧验收。
2. 生产 `rows_read` 变化：clubs 全表每请求多读 20 行，但少读 N 次单行查询；预期净降，未实测（`rows_read` 是计费口径，下次线上诊断可复核）。
3. 并发度对 D1 的实际收益（本地测试库无网络延迟，量化不出来）——真机收益应体现在「少了几趟 RTT」，不是 SQL 变快。

**口径**
1. 只改取数顺序与并发度，**SQL 逐字未改**；响应形状、字段值、排序全部等价（回归用例覆盖）。
2. 选「clubs 全表 + 内存查表」而不是继续加缓存：clubs 就 20 行级，一次取回比按场次逐队查更省，也不受「同名才省」的运气影响；`resolveEntrySide` 留给单场调用方（按需查一次）。
3. CPU 侧花名册绑 `-1` 走索引空集，换取语句位置恒定（`DB.batch` 结果按 `[主, 客]` 下标对齐，不用游标）——语义与原来「不查、回空表」一致。
4. 停赛复算的 entry 集合收窄：不改判定结论（论证见「最坏情况口径」末行 + TC-SUS-15），换来少一趟查询；两侧队伍的数据并发取，赛事库同时 2 条。
5. 列表端点不缓存：数据随录入变化，缓存失效成本高于本次收益；本版只做「不浪费往返」。
