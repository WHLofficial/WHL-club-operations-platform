# 测试计划 · v6.47.0 经济革命 T0 发版批 0：忠诚支出（扣款）+ 取消穷鬼线 + 费率排程 + 开放 2 档维护费下调

> 增量范围：① 忠诚由「奖金入账」改「俱乐部支出扣款」（`delta: -agg.amount`、memo「忠诚支出」、审计 `loyalty_charge`、兜底排程补收官档）；② 新增 config 白名单键 `wage_floor_gap`（默认 `'0'` = 取消穷鬼线）+ `window-payroll` 消费改造；③ `loyalty_tiers` 默认排程固化为 `[[0.5,0.05],[1.5,0.10],[2.5,0.20],[3.5,0]]`；④ `tier_table[1].base_maintenance` 5.0 → 3.5；⑤ 文案/类型连带（worker 注释、web 账本标签与下拉）与 `scripts/prod-20261004-influence-recalc/engine.mjs` 镜像同步；⑥ 两批生产写批工件（**已备未跑**）。
> 设计依据（用户口径）：忠诚 = 俱乐部支出（「loyalty是支出」「这个量级不对」）；逐球员效力时长分档；费率排程 = 效力 0.5/1 收 5%、1.5/2 收 10%、2.5/3 收 20%、≥3.5 不收；扣款时点 = 每赛季第二个正式窗关窗；「T0，但不开窗」；「T3a 提前到此批，并将之前因穷鬼线多扣的退回」。经济模型与数值依据见 `memory/design-s9-income-system.md` §9、`memory/plan-s9-s10-economy-revolution-rollout.md`。

## 范围与风险

**In**：忠诚流水的方向与金额符号、memo 文案、审计 action；收官档（≥3.5 赛季）跳过且不写 0 元流水；`loyalty_tiers` 默认值与「取满足的最高档」语义；`wage_floor_gap` 的默认值/覆盖值/边界（`null` cap、`gap<=0`）与 `wageFloorClubs` 计数、memo 尾注；`CONFIG_KEYS` 白名单长度；`tier_table` 与生成器镜像的一致性；两批生产写批的 SQL 幂等性与账链完整性（本地复刻演练）。

**Out**：任何生产写（`--remote` 执行需用户当轮授权）；`0068` 迁移（转移语义/联盟账户，属 T3b）；媒体池/团结金/entry 池化（T3c）；v4 收入重排（T3d）；前端布局与视觉（本批只有文案与下拉项）；e2e（本批前端零布局/交互变化）。

**最坏情况口径**：
- **方向残留**：若 `delta` 改了一半（例如只改 memo 未改符号）⇒ S9 中期窗按新文案**发钱**，账实相反且比旧行为更难发现。闸门 = 断言 `amount` 为负 + 审计 action 改名 + 全仓 grep 无「忠诚奖金」残留（文档历史留档除外）。
- **顺序风险**：生产写批 A 若**先于**本版上线执行，`loyalty_tiers` 生效而代码仍是旧方向 ⇒ S9 中期窗把 −591.65 发成 +591.65（差 1183.30）。闸门 = README §0 与 manifest `order` 里写明「先发版、后落库」，且批 A 的 verify 含「账本与窗口零改动」断言（执行当下不应有任何 loyalty 流水）。
- **负余额**：账本无下限守卫 ⇒ 4 支次级队（阿森纳/维拉/拜仁/RBL）同窗现金不足会被扣成负值（= 欠款）。这是默认实现的**预期行为**，不是缺陷；若要「归零」或「单列欠款账」须再发版（见待拍板）。
- **费率跨度**：扣款只发生在每赛季第 2 个常规窗、窗刻度每赛季走 2 步 ⇒ 两次扣款之间效力 +1.0 赛季 ⇒ 每份合同共 3 期 = **终身 35% × RC**。口径写错会让「≥3.5 免收」被误读为「5 期/6 期即止」。
- **退回批写错**：批 B 改历史 wage 行而不顺移账链 ⇒ 该队后续每条流水 `balance_after` 全部失真。闸门 = 预检/验收都跑全账本 `LAG(balance_after)` 断点查询（期望 0 行）+ 三队账户 = 最新流水 `balance_after`。
