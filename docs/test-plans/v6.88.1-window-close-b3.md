**投递语义声明：at-least-once，不谎称 exactly-once。** 崩在「notifications 双通道行已写、outbox 行未标 sent」→ 行留 pending/failed → retry 或重投会重复一条；QQ 投递层 `dispatchPendingNotifications` 超时留 pending 重发（notify.ts:341-342 亲证）是正交的第三层重复，B3 不解决。**并发重复面（评审修复轮补登）**：post_close 投递与管理端 retry（或两位管理员同时 retry）可对同一批 pending/failed 行各投一次——行级抢占（收口 UPDATE 带 status 前置）只保证 outbox 状态 / attempt / 计数不互踩，投递动作本身拦不住，重复条数 = 并发投递者数 − 1；前端 retryBusy 只防单端单按钮。TC-B3-05 按此口径断言**多 1 行而非 0 行**（诚实锁重复语义）。

**completed 回放的可达性口径（评审订正，全计划统一）：** closeWindow 定位目标窗只查 `status IN ('open','closing')`，查无抛 409 `'当前没有开着的窗口'`（src/worker/window-machine.ts:572-578 亲证）。**关窗成功后窗口已 closed，重调 closeWindow 在 :578 即 409，到不了 claim、更到不了 :594-598 的 completed 回放**——parity 的 `expectCompletedAndNoReplay`（tests/window-close-parity.test.ts:816-828）锁的正是 409 + 零新行。任何「重调 closeWindow 走 completed 回放」的说法在正常流不成立；要真走 :594-598 必须手工把窗口行 UPDATE 回 `closing` 构造 completed+closing 异常态（TC-B3-06 局 A2）。计划里所有「重调 closeWindow」断言一律按此口径写。

**契约面补充（评审意见⑩，供施工表 shape/route 节同步采纳）：** 投递失败原因目前在管理面不可见（`WindowCloseStatus.notifications` 只有三计数、retry 响应只有三数字，`deliverCloseNotifications` 的 firstError 与行级 last_error 均未透出）。建议：status 端点 `notifications` 加 `firstError`（failed 行首条 last_error）或 retry 响应加 `firstError` 字段（deliver 已返回，契约型同步加可选键）。**若施工表采纳**，TC-B3-09/10 各加一条可选断言（status.notifications.firstError === 行级 last_error 首条 / retry 响应 firstError 非空）；不采纳则登记为已知诊断面缺口，管理员查 failed 原因须直连 D1。

### 1.1 naming_mood 造数法（TC-B3-03 / TC-B3-07 共用，评审⑥落地）

**不可照抄 parity 三局夹具**（moodClubs 全 0、notifications 金样无 naming_mood，parity :477-479 亲证）；也**不可用临时窗**（chargeNaming=false 时 naming 分支整体跳过，home.ts:709 闸 + v3.0.0 裁决注释亲证）。七步：

1. **常规窗**关窗（chargeNaming=true 才进 naming 分支）。
2. **active 冠名合同且 `windows_remaining > 1`**（home.ts:734 门）——`namingContractSql`（parity :149-156）即 windows_remaining=3，可直接用。
3. profile / satisfyCfg 非空由 **DEFAULT 兜底**保证（naming-ops.ts:1405-1408 / :1380-1388，freshEnv config 表无行即走兜底，恒真）——无需造 config 行。
4. **tourTeamId 有映射**：home.ts:689 `tourMap.get(s.club_id)`，真源 = prizes.ts `tourTeamIdsByClub`←AUTH_DB 绑定；seedWindow 绑定段（:130-139）即真源，fixture 里 team.id = clubId。
5. **本库 result_confirmations 造该队胜率过线行**：`INSERT INTO result_confirmations (home_team_id, away_team_id, score_home, score_away, season, window_seq, …)` 两行全胜（home_team_id=tourTeamId、season/window_seq 对上当前窗）→ 胜率 1.0 ≥ 0.5+lineBuffer → sResult=1（naming-ops.ts:1559-1572 查 env.DB 亲证）。
6. delta = `satisfactionDelta(cfg, 0, 1, penaltyMult)` = resultWeight×lineBuffer > 0（sAttend=0：无主场场次，home.ts:735-736；公式 naming-ops.ts:1514-1518 亲证）→ `to ≠ from`（naming-ops.ts:1577-1578）→ moodReports → home.notifications 推 naming_mood（home.ts:748-750 + :815-827，data 含 club/brand/from/to/reason）。
7. **单测前置闸**：先把 `evolveSatisfactionForClub` 拉出来单测（直接调用断 `report.to !== report.from` 且 `delta > 0`），绿了再进关窗链路——防「永远空转的断言」（评审⑥原话口径）。

naming_terminated / naming_offer / naming_offer_activated 三模板**不做端到端造数**（terminated 涉及 satisfyFloor 终止阈值、offer 系涉及招商轮，造数成本高且不改变 staging 代码路径——四模板共享同一条 home.notifications 循环）；多行不互吞由 TC-B3-12 单元面承担，payload 键多样性由 TC-B3-04（squad）+ TC-B3-03（naming_mood）双点覆盖。此取舍如实登记，不再假装覆盖。
