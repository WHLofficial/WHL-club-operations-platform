### 3.1 12 cause × from 态矩阵（TC-MX-01…10）

**种子形状（单故障原则）**：每格一行 `listings`，`status` = 该格的 from；`deadline_note`、`last_bid_at`、`activation_deadline`、`match_deadline`、`deadline_at`、`bid_paused` 六列**预置哨兵**（`'SEED-NOTE'` / `'2020-01-01T00:00:00.000Z'` / `1`）——"没动"这件事只有哨兵能证明。**但每格只允许"被测的那一个条件"为假**，其余守卫的输入必须预先摆成"能通过"的形状，否则 `changes=0` 无法归因（会掩盖真守卫）。因此按 cause 注入背景：

| cause 分组 | 背景注入（除 status 外的守卫输入） | 理由 |
| --- | --- | --- |
| `first_bid` | `deadline_at = NULL`、`activation_deadline = NULL`（两窗全开）；`last_bid_at` 仍置旧哨兵以证被覆盖；`match_deadline` 置未来哨兵 | 语句守卫是 `deadline_at IS NULL OR > now` **AND** `activation_deadline IS NULL OR > now`（`src/worker/routes/market.ts:1234-1236`）。**哨兵若是过去时刻（字符串比较为假）或整数 `1`（SQLite 类型序 INTEGER < TEXT，比较恒假），合法格会全部落成 `changes=0`** —— 本版初稿即踩此坑，评审 F1 命中 |
| `forced_cancel` | **每一格**（含非法格）`type = 'forced'`；`type` 作为变量的对照只在 TC-MX-04 出现 | 让 `changes=0` 只可能来自 status 守卫 |
| `admin_reset` | 合法格无任何 `bids` 行；有 bid 的对照只在 TC-MX-08 | `NOT EXISTS (active bids)` 是第二道守卫 |
| `settle_for_review` / `activation_match_start` | `params.fromStatus` = 该行真实 from | 守卫是 `status = ?`（参数），不是 `IN` 常量集 |
| 其余 8 个 | 无附加背景（守卫只有 status，`type`/时间列/note 都不参与 WHERE） | —— |

`bids` / `fund_holds` / `players` 等关联表在矩阵用例里**一律不种**（除非该 cause 的守卫要求），避免关联行把 `changes` 的归因搅浑。

**矩阵规模**：from 轴 = `listed` / `bidding` / `matched_pending` / `pending_review` / `delisted`（五个值全部在 `src/` 里实际出现，已扫证）⇒ 12 × 5 = **60 格**，其中**合法 21 格**（清单：first_bid 2、activation_match_start 2、settle_for_review 3、unbid_expired 1、activation_price_expired 1、admin_reset 1、admin_cancel 2、forced_cancel 2、matched_kept 1、negotiation_closed 1、review_rejected 1、deal_done 4）、**非法 39 格**。

## 7. 风险与最坏情况

- **参数错位（最高危）**：`advanceStatement` 的 `params` 是对象，模板内 `?` 顺序一旦与 `bind` 顺序不一致（如 `first_bid` 的 `deadline_at` 与 `id` 互换），D1 不会报错、只会静默写错值。TC-COL-01/02 的行为断言是唯一防线；TC-COL-03 的列名锁挡不住**顺序**错，故 3.1 每个合法格都必须断言"改的是这一行的这一列"（校验 `id` 未被动过 + 目标列值）。
- **`nowSql()` 内联 vs 绑定**：`first_bid` 的 `last_bid_at` 现为 SQL 表达式内联（`src/worker/routes/market.ts:1233`）。若实现改成绑定参数，时间戳来源从「D1 服务器时钟」变成「Worker 进程时钟」，**跨时区/时钟漂移下 `deadline_at` 判定会漂**——TC-COL-02 的正则断言刻意只验"SQL 侧写入的形状"，但真正的等价性是"仍由 SQL 生成"，评审需人工确认模板里没有把该列变成 `?`。
- **`deal_done` 收敛（v6.66.0 疤痕回归）**：它是四态 catch-all，与 `matched_kept`、`review_rejected`、`unbid_expired` 的 from 集重叠。任何"去掉重叠"的整理都会让某条真实路径（成交后挂单停在 `pending_review`）重新变成脏行 —— 生产症状是球员被 `ensureNotInFlight` 一票否决（续约/解约/海捞/上调全拦），2026-11-01 已发过一次。TC-MX-01 的 `deal_done × 四态` 是这条疤痕的唯一常驻锁。
- **`activations` 的 `results[2]`**：运行时代码按下标读 changes 判 409（`src/worker/activations.ts:302`）。若 `advanceStatement` 内部偷偷多包一条语句（例如缓存校验），下标整体平移，409 分支会读错语句的 changes —— 要么永不触发、要么误触发。TC-ORD-01 的下标锁 + TC-SRC-03 的"恰一条语句"是双保险。
- **两个非 status 写入被误收编**：`market-settle.ts:547`（note 刷新，带 `status IN ('listed','bidding')` 写闸）与 `routes/admin/market.ts:105`（`bid_paused`）看起来"也是 listings 写入"。收编它们会改变读路径的写行为（note 刷新是 `db.batch` 分块 ≤90 的性能敏感路径，`market-settle.ts:552-557`）。TC-SRC-04 是反向锁。
- **触发器与语句守卫的"同源双写"**：0040/0059 的守卫读 `listings` 当前列值，`BEFORE INSERT ON fund_holds` 让它在 listings 语句之前跑。但**顺序不是防线**：触发器两分支恰是 `first_bid` 语句 WHERE 守卫的逐字补集（`deadline_at IS NOT NULL AND <= now` ↔ `IS NULL OR > now`），且端点预检在批构造前就读过陈旧行（`routes/market.ts:1147-1148`、`:1152-1153`）⇒ 确定性种子下"把语句前置"既不会放行也不会拦截出差异（评审 F2）。真正的风险是**单侧漂移**：只改语句守卫或只改触发器，会出现"语句放行但触发器 ABORT"（用户看到 500 而非干净 409/no-op）或"触发器放行但语句空转"（过期单被静默无视）。防线 = TC-TRG-05 文本成对性 + M11 变异；`first_bid` 的批内下标 4 只是等价性锁。
- **已知不可测项（如实登记，不假装覆盖）**：批内两条语句之间 `strftime('now')` 的亚毫秒差会让"预检通过、语句守卫已过期"这一窗口出现，此时冻结与状态更新可能不同步。该窗口**不可确定性种入**（需要把 deadline 摆在两条语句求值之间的毫秒级位置），故不设用例，也不在验收口径里声称已覆盖；改码时保持语句顺序不变（L6）即可保证该窗口与改前同宽。
- **文案逐字锁的脆弱性**：8 条 note 文案（5 固定 + 3 参数化模板）是用户可见契约，逐字锁意味着**改文案必须改测试**——刻意为之（判级 patch 的定义），不是过度约束。`negotiation_closed` 的三处调用方文案更要注意：它们由调用方拼好传入，本版**不该**在实现里出现任何中文文案字面量（TC-NT-04 的源码断言）。

## 8. 与语义卡/任务书的偏差报备（如实登记，不静默吸收）

1. **批形态 11+1，不是 10+2**：语义卡称"12 处写点里 10 处是 `db.batch` 内的一条语句"，实测为 **11 处批内 + 1 处独立 `.run()`**（`activation_match_start`，`src/worker/market-settle.ts:339-344`；`delistUnbid` 的 batch 在 `:226`）。本计划按实测登记，TC-SRC-03「独立执行版恰用于 `activation_match_start`」与实测一致。
2. **note 分类按代码实测定为四类**：任务书转发的卡①「note 三态」在转发中截断（止于 `activation_price_expired` 的文案），无法据此裁定分类数；本计划逐格读码后定为 **5 固定 + 3 参数化 + 1 置 NULL + 3 不碰 = 12**（§1 L4），与 12 个写点逐格吻合。
3. **触发器耦合的机制改写**：任务书⑤把它表述为"附带列更新顺序与条件保持原样"。实测顺序对"拦/放"**不可观测**（预检在批前 + 触发器条件与语句守卫互为补集），故把验收重心从"顺序防洗白"改为"两处条件文本必须成对同步"（TC-TRG-05），下标 4 降级为等价性锁；原"先写 listings 再冻结 = 洗白通道"的论述作废（评审 F2 指出，已复核确认）。
4. **本轮评审（8 条）落点对照**：F1 种子与 `first_bid` 守卫矛盾 → §3.1「背景注入表」+ TC-COL-02 三组合；F2 `first_bid` 顺序不可复现 → L12 / TC-TRG-04 / 新增 TC-TRG-05 / §7 改写；F3 三处下标无锁 → 新增 TC-ORD-04 + §1.1 语句位列补依赖说明；F4 优先级计数 → §3 标题改为 P0×25 / P1×6 / P2×1（新增两例后总数 32）；F5 函数名 → `cancelForcedAuction` / `submitMatch`；F6 `parseReason` → `requireReason`（附 400 文案）；F7 TC-COL-02 三组入参写全；F8 本节。
