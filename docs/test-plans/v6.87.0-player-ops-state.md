## 7. 风险与最坏情况

- **参数错位（最高危）**：`restoreAfterListing` 的 bind 是 `(playerId, playerId, listingId)` 三参（母本形态），占位符顺序一旦与 bind 不一致 D1 不报错、只静默写错。TC-CTX-01/02 的行为断言 + TC-GRD-01 的占位符计数是双防线。
- **CASE 分支顺序**：club_id 必须优先于合同判定——若实现把合同判定放前，free + 残留 active trainee 合同的脏行会落 `trainee`（幽灵复活）。TC-CTX-01 的 (NULL, trainee) 格是唯一防线，**不允许"顺手统一"分支序**。
- **`transfer_terms` 的重写语义**：二跑 = 1（同值重写，不挂 gate）。任何"顺手加同值排除"会改变幂等分层（入口 terms_applied 短路才是幂等真源）——TC-MX-06 特例钉住。反向同理：`import_sync` 的反向自限若被"统一"成 IN 守卫，listed/free 行会被误碰——TC-PRM-03 钉住。
- **语句位平移**：`activations.ts:301`（results[2]）、`offers.ts:536`（results[1]）、`bypass.ts:781`、`activations.ts:166` 都是下标硬耦合；`advanceStatement` 内部多包一条语句即整体平移、409 分支读错语句的 changes。TC-GRD-01（恰一条语句）+ TC-ORD-02（下标锁）双保险。
- **EXISTS 守卫与 D1 batch 串行可见性**：守卫读同批先行语句的落库值。本地 better-sqlite3 夹具与生产 D1 在这一点上的等价性没有独立证明，但 `delistUnbid` 的 P1-1 修复（`market-settle.ts:179→184`，已在生产运行）已依赖同一机制 ⇒ 风险等级不因本批升高；六条依赖链的翻红负例（TC-ORD-03）在本地引擎上验证语义。
- **`negotiation_void_restore` 的 null 透传**：listingId=null 时不得被恒假 EXISTS 吞掉（match 单/无挂牌单据）。TC-CTX-02 ③ + TC-ORD-03 重序不翻红的双向钉。
- **`playerRestoreSql` 删除的扩散风险**：留薄封装会让无守卫版继续扩散一个入口——TC-SRC-02 的标识符 0 命中锁。
- **已知不可测项（如实登记，不假装覆盖）**：批内 `strftime('now')` 亚毫秒竞态（同 v6.83.0 §7，本批不改批序故窗口与改前同宽）；生产存量幽灵行（B1 错位 / B2/B3 幽灵 normal）规模未知，测试只覆盖增量行为——存量订正需单独授权的只读探针 + 数据批（registered#1）。
- **`demote` 的 settledGuard 字符串拼接**：守卫文本内嵌 `${playerId}/${clubId}` 字面量是现状（`promotion.ts:202-206`），收编保持字符串透传（TC-PRM-04）；若施工顺手改参数化属**运行时变化**，超出本批判级，评审须拦。
