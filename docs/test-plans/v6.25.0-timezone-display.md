# 测试计划 · v6.25.0 显示时区偏好化（qa-test-planner）

spec：`docs/superpowers/specs/2026-10-03-timezone-display-design.md`。基线：vitest **73 文件 / 1265 例**（v6.24.1 收口后实测，含 5393109 的 +1 与本计划落稿前新增文件的预估差，执行时以当时实际为准回填）。口径：**内部 UTC 不动、显示层偏好化、默认北京**；倒计时与服务端判定零改动。

## A 组 · 共享时间层 `web/src/lib/datetime.ts`（vitest，jsdom）

- **TC-A01 默认北京** P0：清空 `whl.tz` → `fmtDateTime('2026-10-03T13:00:00Z')` = `2026-10-03 21:00`、`fmtTime` = `10-03 21:00`、`fmtDate` = `2026-10-03`。
- **TC-A02 UTC 档** P0：`localStorage.setItem('whl.tz','utc')` → 同一输入渲染 `2026-10-03 13:00`（无 +8）。
- **TC-A03 非法值回落** P1：`whl.tz='bogus'` → 按默认北京渲染；不抛错。
- **TC-A04 非法输入** P1：`fmtDateTime(null)` / `undefined` / `''` / `'not-a-date'` 全回 `'—'`。
- **TC-A05 setTzPref 派发事件** P0：`setTzPref('utc')` 后 `whl:tz-change` 事件可被 window 监听收到；localStorage 值已写。
- **TC-A06 useTzPref 订阅重渲染** P0：挂载使用 `useTimeFmt()` 的组件 → `act(() => setTzPref('utc'))` → 渲染文本变化（证明消费端走 hook 会刷新，这是本增量的头号失效模式）。
- **TC-A07 storage 事件跨标签页** P2：`useTzPref` 组件挂载下，另一上下文写 localStorage 并派发 `storage` 事件（jsdom 手动 dispatch）→ 组件更新。
- **TC-A08 system 档烟测** P2：`whl.tz='system'` → 渲染不抛错、非 `'—'`（CI 时区不定，不做精确断言）。
- **TC-A09 formatter 缓存不串档** P1：北京渲染 → 切 UTC 再渲染 → 切回北京 → 首档结果逐字复现（Map 缓存按 pref+opts 分键，防串）。

## B 组 · 顶栏图标化（TopBar）

- **TC-B02 下拉与选中态** P1：点击展开 `.tz-pop` 三项、当前项带 `✓` 与 `aria-checked`；点选 UTC 后偏好生效（页面时间随之变化）且下拉关闭。
- **TC-B03 外点/Esc 关闭** P2：展开后点击下拉外区域 / 按 Esc → 关闭。

## 最坏情况口径

- **TC-A06/V1 是主战场**：订阅失效是「测试单测全绿、用户侧却要刷新才生效」的静默失效——必须在组件挂载态下断言（不能只测纯函数）。
- **9 处消费点逐一清点**：静态锁 TC-D02 兜底「漏改」，但「改了却没走 hook」只能靠 V1 式挂载断言 + 评审核对；手验抽样至少覆盖 C01/C04/C05 三页。
- **system 档**在 CI 与用户机器时区不定：精确断言写在北京/UTC 两档，system 只烟测——这是刻意取舍，不算缺口。
- **本地化输出形态**：Intl 版本差异可能让 `formatToParts` 的 hourCycle 输出变化（如 `24:00` 边界）——TC-A01 用 `13:00Z` 避开午夜边界；`23:xx`/`00:xx` 边界补 TC-A10（P2）：`2026-10-03T15:59:00Z` 北京 = `2026-10-03 23:59`、`16:01:00Z` = 次日 `00:01`（跨日进位正确）。
