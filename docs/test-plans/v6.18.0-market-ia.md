## 附带修复：`src/worker/rumors.ts` 事实池字段名不匹配（计划外，已确认）

本计划开工前的复现（内存 D1 + 全量迁移 + 真实 `buildRumors` 调用）发现该文件的事实池读取整片错位：SQL 出的列名是 snake_case（`player_id` / `seller_club_id` / `club_name` / `player_name` / `club_id` / `to_club_id` / `to_club_name`…），代码与 `SaleFact` / `DealFact` / `FakePlayer` 接口却按 camelCase 读（`fact.playerId` / `fact.clubName` / `player.clubId` / `s.clubId` / `d.toClubId`…）。`all<SaleFact>()` 的泛型断言让 `tsc` 查不出来，实测三类后果：

1. 真传闻 5 条文本里出现字面 `undefined`（`{player}` / `{club}` 未被替换），载荷缺 `playerId` / `playerName` / `clubName`（`JSON.stringify` 丢弃 `undefined` 键）——情报页既显示不出球员名，也点不进球员页（玩法「自行查证」直接失效）。
2. 假料守卫两条全部失效：`player.clubId` 恒 `undefined` ⇒ 「不指向球员现效力队」不生效（实测 3 条假料全部指向球员现效力队「甲队」）；`s.playerId` / `d.toClubId` 恒 `undefined` ⇒ 「不与真实关系重合」不生效。
3. 成交池兜底恒空：`fact.toClubName ?? fact.fromClubName ?? ''` 恒为 `''` ⇒ 在售池为空、成交池有数据时，真料槽被整块 `continue` 丢弃（该场景下只剩假料）。

修复（只动这一个文件、三处 SQL）：给事实池三条查询加 `AS` 别名，使列名与既有接口/读取一致——`l.player_id AS playerId`、`l.seller_club_id AS clubId`、`cl.name AS clubName`、`${sqlDisplayName('p')} AS playerName`（成交池同 rule，另加 `toClubId` / `fromClubId` / `toClubName` / `fromClubName`）、假料池 `p.club_id AS clubId`。不带别名的老写法在本仓是错的：D1 按 SQL 列名给键，不会做 camelCase 转换。

锁定：TC-RUMOR-01 / 04 断言每项键集完整、文本不含 `undefined` 与 `{player}` 占位符；变异 V11（把别名改回 snake_case 列）必须让这两条红。

## 最坏情况口径（铁律）

- **最坏情况**：判分表把海捞名单换成批量端点后，批量快照与详情页判定漂移（详情说能签、名单说不能签，或反之），球员在两个页面看到互相矛盾的原因，用户拿着截图来质问。机制：`market.ts` 的 4 条批量查询与 `bypass.ts` 的守卫链是两份代码，任一处改口径（加关、删关、换顺序、改文案）都不会被单侧用例发现。→ TC-LOOKUP-05（逐球员与 `GET /api/players/:id` 的 `seaSign` 深比较 + 文案逐字）+ 变异 V4。
- **最坏情况**：传闻的「同窗内恒定」被人为（缓存键漏了窗口号）或算法侧（种子漏了 windowSeq）打破——同一窗口刷新两次内容跳变，或者两个窗口内容完全一样（换窗不换血），玩家会说「这游戏在随机糊弄我」。机制：`cachedJson` 键 `market-rumors:{season}:{windowSeq}` 与 `buildRumors` 的 seed `[season, windowSeq]` 是两处独立记忆点。→ TC-RUMOR-03、TC-RUMOR-08 + 变异 V1、V9。
- **最坏情况**：假料把真人真事讲出「不存在的关系」——例如造出「甲队已和甲队自己的球员谈妥」，玩家一眼看穿是编的；或者本窗被解约的球员在传闻里被写成即将加盟，与 4.4.4 禁签规则打架。机制：假料放置时的两条守卫（不与真实关系重合、不指向球员现效力队）被当成冗余删掉。→ TC-RUMOR-05 + 变异 V3。
- **最坏情况**：成交公示丢了 termination 行（解约在公示栏消失，用户以为解约没生效）。机制：`transfers.from_club_id/to_club_id` 在 termination 上有一侧为 NULL，有人把 LEFT JOIN「统一」成 INNER JOIN。→ TC-DEAL-04 + 变异 V5。
- **最坏情况**：公示表随历史数据增长退化成全表扫 + 临时排序（0058 索引形同虚设，页面首屏拖慢）。机制：ORDER BY 顺序与索引定义（`status, completed_at DESC, id DESC`）错位，或 WHERE 里加了个让优化器放弃索引的谓词。→ TC-DEAL-06 + 变异 V6。
- **最坏情况**：激活名单把本队球员列出来（自己激活自己的球员，白扣违约金），或 `?mode=trainee` 混进正式球员（青训专属通道被拿来做低价激活）。机制：`p.club_id != ?` 过滤被误删、两 mode 的行集条件写反。→ TC-ACT-02、TC-ACT-03 + 变异 V7、V8。
- **最坏情况**：名单人数不受控（`limit` 失效或钳制上下界写错），一页拉出全联赛球员，页面卡死且暴露非本页所需的球员工资 / 合同细节。机制：`Number.isInteger` 判定与 `Math.min(100, Math.max(1, n))` 的钳制被简化掉。→ TC-ACT-06 + 变异（钳制删除：`limit=0` 返回空、`limit=200` 返回 >100 条即红）。
- **最坏情况**：本窗激活额度（一窗一次）在名单上看不出来——用户点第二次才撞 409「本窗口已经被激活过」，白写一次申请。机制：`activatedThisWindow` 的查询漏了 type='activation' 或漏了 season/window 双键。→ TC-ACT-09。
- **最坏情况**：退役的三个老端点被前端缓存 / 老书签继续打，返回 200 空数组而不是 404，让「已退役」和「当前无数据」混同，排障时查不出来。机制：路由只删了实现没删注册，或者留下了 200 的空壳。→ TC-REG-01。
- **最坏情况**：新缓存作用域的接入只改了一半——purge 清单里没有 `market`（传闻被污染后清不掉），或写路径映射漏了 `/api/market`（管理侧改完市场数据，公示一小时不更新）。机制：`PUBLIC_SCOPES` 长度断言与 `scopesForWritePath` 数组字面量散在三个测试文件里，只改一处就绿。→ 缓存三件套改写（本清单外，属回归项）。

## 用例

### TC-RUMOR 传闻（GET /api/market/rumors）

**TC-RUMOR-01 · 载荷结构与 id 序列**（P0 · vitest）

- 前置：夹具 `seedRumorFixture()`——开窗 (4,1)、在售池 2 笔（S1 甲队 listed / S2 乙队 bidding）、假料池按种子抽出的 48 个 id 全部灌入（club 101 甲队、status normal）、`PUBLIC_CACHE_TTL_MS='0'`。
- 步骤：教练 `GET /api/market/rumors`。
- 预期：200；`rumors` 长度 8；每项键集恰为 `['clubName','id','playerId','playerName','text']`（无真 / 假标记、无事实池细节）；`id` 序列恰为 `r4-1-0` … `r4-1-7`（升序，与槽位一一对应）。

**TC-RUMOR-02 · 同窗两次请求逐字相等**（P0 · vitest）

- 前置：同上（TTL=0 ⇒ 每次请求都真跑生成器，第二次不是缓存给的稳定）。
- 步骤：连续两次 `GET /api/market/rumors`。
- 预期：`JSON.stringify(a) === JSON.stringify(b)`；且两次都非空（长度 8）——若生成器退化成 `Math.random` 或时间戳入种，本条红。

**TC-RUMOR-03 · 换窗换血（种子含 season + windowSeq）**（P0 · vitest）

- 前置：同上；`UPDATE season_windows SET window_seq = 2 WHERE season = 4`（同一赛季换窗）。
- 步骤：(4,1) 取一次 → 换成 (4,2) → 再取一次。
- 预期：两载荷 `JSON.stringify` 不等；第二次 `id` 前缀全为 `r4-2-`；第二次的 `(playerId, clubName)` 关系集合与第一次不同（本夹具下 (4,2) 的假料 id 抽签落在库里不存在的号段 ⇒ 假料槽被丢弃，条数 3，`id` 为 `r4-2-5/6/7`——条数变化本身也是「换窗换血」的证据）。若种子漏了 windowSeq（V1），两窗内容（除 id 外）完全相同、且第二次仍出 8 条 → 本条红。

**TC-RUMOR-04 · 真假混排与模板不重复**（P0 · vitest）

- 前置：同上（在售池 2 笔、假料池 48 人）。
- 步骤：取一次载荷。
- 预期：真料 5 条——`playerId` ∈ {S1, S2} 且 `clubName` 与在售关系逐一对上（S1→甲队、S2→乙队），真料条数 = 5（槽 0/2/3/4/6）；假料 3 条——`playerId` ∈ 种子抽出的造号 id 集合（48 个）且 `playerId` ∉ {S1, S2}；8 条 `text` 互不相同（同模板不重复使用）；每条 `text` 都不含未替换的 `{player}` / `{club}` 占位符。

**TC-RUMOR-05 · 假料守卫（两段：现效力队 + 真实关系撞车）**（P1 · vitest）

- 前置：同上（在售池 2 笔、造号池 48 人全挂甲队）。
- 步骤（段一）：取一次载荷，按「假料 = `playerId` ∈ 造号池」挑出 3 条。
- 预期（段一）：对每条假料，`clubName` ≠ 该球员现效力队名（甲队）——造号池全体挂甲队，三条假料必须全部避开甲队（实测落在乙队）；且 `(playerId, clubName)` 不在真实在售关系集 `{(S1,甲队),(S2,乙队)}` 内。
- 步骤（段二，撞真实关系守卫的可达口径）：补一条在售 listings，使 `player_id` 恰为槽 1 首轮落点那个造号球员（`19640`）、`seller_club_id` = 乙队；再取一次载荷。
- 预期（段二）：`rumors` 长度 7 且 `id` 序列不含 `r4-1-1`——槽 1 首轮组合（19640 × 乙队）与真实在售关系重合被跳过、次轮又落回甲队（现效力队）被跳过、三轮用尽即丢槽；段一里 `r4-1-1` 是存在的（差分已证）。删掉撞关系守卫（V3 的另一半）→ 段二长度回到 8 → 红。
- 理由：段一锁「不指向现效力队」；段二用「补真实关系 ⇒ 该槽消失」把「不与真实关系重合」从死代码变成可观察行为（否则该守卫只在造号池球员恰好出现在在售/成交关系里时才可达）。

**TC-RUMOR-06 · 事实池空/半空时的分支落点**（P1 · vitest）

- 前置：同夹具但**不灌**任何 listings / 市场类 completed transfers（在售池、成交池皆空），假料池照灌。
- 步骤（段一）：取一次载荷。
- 预期（段一）：仍 200；真料槽因事实池空而**落回假料分支**，`rumors` 长度 7（槽 1~7；槽 0 三轮抽签全部落在甲队 = 现效力队而被丢），7 条全部满足假料口径（`playerId` ∈ 造号池、`clubName` ∈ {乙队, AC米兰(CPU)} 且 ≠ 甲队），无一条带真实球员 id——若把「无事实可用」处理成跳过而不是落回假料，条数会明显小于 7。
- 步骤（段二）：补一笔 `type='transfer'`、`status='completed'` 的成交（`to_club_id` = 甲队），`q` 不变再取一次。
- 预期（段二）：长度 8；真料槽改用成交池兜底（5 条 `playerId` = 该成交球员、`clubName` = 甲队），假料仍 3 条；若成交池的 `toClubName ?? fromClubName` 读成 `undefined`（曾发生的字段名错位），`clubName` 会变 `''` 从而整槽 `continue` 丢弃 —— 长度掉到 7 以下即红（V11 的第二种指纹）。
- 理由：真料槽「无事实可用」时的落点是产品口径（宁可出假料也不空窗），成交池兜底是唯一在售池为空才会走的分支。

**TC-RUMOR-07 · 不泄漏内部标记与池字段**（P1 · vitest）

- 前置：同上（真假混排的标准夹具）。
- 步骤：取一次载荷，`JSON.stringify` 全文检索。
- 预期：全文不含 `truth` / `fake` / `isTruth` / `真假` / `template` / `slot` / `seed`；每项键集与 TC-RUMOR-01 白名单一致（`id` / `text` / `playerId` / `playerName` / `clubName`，不多不少）。

**TC-RUMOR-08 · 缓存命中与缓存键含窗口**（P0 · vitest）

- 前置：`PUBLIC_CACHE_TTL_MS='60000'`（本例单独覆盖，其他用例为 `'0'`）。
- 步骤：取一次 → 往库里补一笔在售 listings（不 purge）→ 再取 → `UPDATE season_windows` 换窗到 (4,2) → 再取。
- 预期：第 2 次与第 1 次逐字相等（命中缓存，改库不出新值）；第 3 次 `id` 前缀为 `r4-2-`（键含 windowSeq ⇒ 换窗必换键必重算）。若缓存键漏了 window/season（V9），第 3 次仍回旧载荷（`r4-1-*`）→ 本条红。
- 理由：本条的缓存键断言不靠读源码字符串，而是靠外部行为（换窗后必须出新值）——比断言 `cachedJson(`market-rumors:${...}`)` 文本更抗重构。

**TC-RUMOR-09 · 匿名可读 + 限流先于读库**（P1 · vitest）

- 前置：同上；`resetGuards()`（清限流桶与 L1 缓存）。
- 步骤：无 Cookie 连续 `GET /api/market/rumors` 60 次，第 61 次再打；随后补一笔在售数据再打一次。
- 预期：前 60 次全 200；第 61 次 429 且 `{error:'请求太频繁，请稍后再试'}`；补数据后再打仍 429（限流先于读库、不落缓存）。
- 理由：传闻是公开端点，限流是唯一挡住消耗战的护栏；桶按 IP（测试里缺省 `local`）计数，`resetGuards` 保证不被前序用例污染。

**TC-RUMOR-10 · 无开窗时用可见赛季兜底（windowSeq 0）**（P2 · vitest）

- 前置：`UPDATE season_windows SET status='closed'`（无开窗）；seasons 表补 `(5, 'preparing')`，保留 `(4, 'running')`。
- 步骤：取一次载荷。
- 预期：200；`id` 前缀全为 `r4-0-`（用可见赛季 4——`running` 优先于更高赛季的 `preparing`；窗口号兜底 0）；且不因无开窗而报错 / 空数组。
- 理由：休赛期也要能看传闻（否则玩家以为功能坏了），兜底窗口的口径（赛季取可见赛季、窗口号取 0、且不参与缓存键的窗口歧义）在 id 里直接可读。

### TC-DEAL 成交公示（GET /api/market/deals）

**TC-DEAL-01 · 7 种 type 全出且金额语义原样**（P0 · vitest）

- 前置：夹具灌 7 种 type 各一行（`transfer` / `activation` / `forced_auction` / `free_agent` / `listing_sale`（若为既有 type 集之一）……实际按 `transfers.type` 现存取值全集列出），全部 `status='completed'`，其中若干笔带 `extra_fee`，一笔 `fee` 为 NULL。
- 步骤：教练 / 匿名各 `GET /api/market/deals`。
- 预期：200；7 行全在；`{id,type,playerId,playerName,fromClubName,toClubName,fee,extraFee,season,windowSeq,completedAt}` 键集齐；`fee`/`extraFee` 原样透传（NULL 仍为 `null`，不做 0 填充）；`completedAt` 原样（UTC 字符串）。
- 理由：公示页要把 fee 与 extra_fee 分开展示，任何一处被 `?? 0` 抹平，用户看到的成交价就不是实际价格。

**TC-DEAL-02 · 排序 completed_at DESC, id DESC**（P0 · vitest）

- 前置：灌 4 笔，其中 2 笔 `completed_at` 同一时刻（连号 id）。
- 步骤：取一次载荷。
- 预期：`completedAt` 非升序排列；同刻的两笔按 `id` 降序（后成交的在后登记者排前面——`ORDER BY completed_at DESC, id DESC` 的次键）。

**TC-DEAL-03 · LIMIT 50**（P0 · vitest）

- 前置：灌 55 笔 completed（`completed_at` 严格递增、id 递增），另加 5 笔非 completed。
- 步骤：取一次载荷。
- 预期：长度恰 50；取到的是最近 50 笔（即 55 笔中 `completed_at` 最大的那 50 个 id 集合逐元素相等，最旧的 5 笔不在其中）；非 completed 的 5 笔一律不在。

**TC-DEAL-04 · LEFT JOIN 两侧（termination 行不得丢）**（P0 · vitest）

- 预期：两行都在；`toClubName` / `fromClubName` 对应侧为 `null`（不是 `undefined`、不是空串、不是 `'未知'`）。若把 LEFT JOIN 改成 INNER JOIN（V5），缺侧的行整行消失 → 长度断言与本条红。

**TC-DEAL-05 · 只出 completed**（P0 · vitest）

- 预期：恰 1 行（那笔 completed）；其余 4 笔的 id 一律不出现（防止把「在途」也算成成交公示）。

**TC-DEAL-06 · 查询计划与 SQL 文本锁**（P0 · vitest）

- 前置：灌 55+ 笔 `status='completed'`（逼优化器有机会选错计划）+ 40 笔其他 status；`captureSql(fx)` 包装 `env.DB.prepare` 收集 SQL 文本。

## 发现的 src 缺陷（只报告，未修）

**激活名单在「正式合同无违约金」时整页 500**（`GET /api/market/activatable`）

- 复现（内存 D1 + 全量迁移，`tests/market-activatable.test.ts` 的夹具手法，临时探针跑完即删）：给乙队一名 `status='normal'` 球员挂一份生效 `formal` 合同，`release_fee` 置 `NULL`（或 `0`），以绑定教练身份请求名单。
- 实测：三发全部 500 —— 默认 limit、`?limit=1`（该行 CA 最高、必在第一页）、以及 `release_fee=0` 变体，响应体 `{"error":"服务器出了点问题，请稍后再试"}`；服务端日志 `[api] 未处理错误: RangeError: 违约金须为正数`。
- 机制：`src/worker/routes/market.ts:550` 的映射对每行调 `activationFee(r.release_fee ?? 0, r.protection_ticks, currentTicks)`，而 `src/core/bypass-rules.ts:45` 的 `activationFee` 对非正数直接 `throw new RangeError('违约金须为正数')`；`NULL ?? 0` 恰好落进这个分支，抛出点在 `.map()` 里、路由未捕获 ⇒ `app.onError` 兜底成 500。**一名这样的球员就能让整份名单打不开**（不是跳过该行）。
- 同仓既有的正确处理：`src/worker/bypass.ts:287` 与 `:370` 对同一状态显式挡下——`if (!contract || contract.release_fee === null || contract.release_fee <= 0) throw new HttpError(409, '球员没有含违约金的现行合同，先让管理组补合同')`。`contracts.release_fee` 在 `0001_init.sql:57` 可空，写入侧（`contracts-import.ts` / `transfers.ts`）也确实可能落 `NULL`，所以这不是理论态。
- 建议（未实施）：名单侧比照 `bypass.ts` 处理——要么在 `activationFee` 前先判非正数、该行 `activationFee: null` 并让前端显示「缺违约金，待补合同」，要么在 SQL 里过滤掉这类合同（但那样球队就看不到待补合同的球员）。修复属 src/ 改动，按本任务口径只报告。
