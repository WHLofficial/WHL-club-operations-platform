> 按 qa-test-planner 约定设计：TC 编号即执行层 vitest 用例名（建议落 `tests/growth-match-entry.test.ts`，`describe('TC-LIST') / describe('TC-PANEL') / describe('TC-BATCH')` 分组；前端复算纯函数落 `web/src/lib/growth-xp.test.ts` 或并入同文件，TC-UI 走 e2e/手动）。
> 承载文件：`src/worker/routes/admin/growth.ts`（3 个新端点）、`src/worker/results.ts`（可计 XP 口径常量复用/对齐）、`web/src/pages/admin/GrowthEntryPage.tsx`（新页）、`web/src/pages/admin/PlayersPage.tsx`（删单人补录表单）、`web/src/lib/api.ts` + `adminQueries.ts`（类型）、`web/src/lib/growth-xp.ts`（复算纯函数）。
> 用例总数 34（P0 24 / P1 8 / P2 2）；变异验证清单 5 条。

## 范围

**In scope**

- `GET /api/admin/growth/match-entry`：可补录比赛列表（可计 XP 口径过滤、近 50 场、每场已录事件数、两队 club 解析、CPU/未建档标记）。
- `GET /api/admin/growth/match-entry/:matchId`：单场面板数据（两队花名册、该场已录事件预填、训练营标注）。
- `POST /api/admin/growth/match-entry/:matchId`：批量补录（5 类白名单、口径复用单人规则、同锚去重、单批原子、审计一条、结算响应）。
- 前端：GrowthEntryPage 交互（列表/展开/切换/脏检测/保存回填/XP 复算/锁定）、旧单人补录表单删除回归。

**Out of scope**

- 球员卡成长页签（增量 B 被用户砍掉，Player.tsx 零改动）。
- goal/assist 人工补录（本版只读展示自动已录值）；成长事件删除/纠正通道（平台本就没有，如实标注）。
- 赛果确认流程本体；`xpForEvent` 口径变更（只复用）。

## 最坏情况口径（铁律）

- **同锚去重被绕开 = 重复发 XP**：若 matchRef 不用比赛 id（如 manual:时间戳），UNIQUE 锚失效，同一格重提交会重复加 growth_xp。→ TC-BATCH-06 + 变异 V1
- **club 归属校验缺失 = 越权录入**：不给该场两队的孩子录数据，台账就脏了且审计看不出异常。→ TC-BATCH-03 + 变异 V2
- **两端口径漂移**：前端实时复算与后端 xpForEvent 各写一份，将来只改一边就会「界面显示 +3、入账 +2」。→ TC-UI-XP + 变异 V3
- **口径过滤漏掉弃权场**：walkover 场不计 XP（results.ts 同口径），列出来录了白录且永远 duplicate 不了（自动通道根本没写）。→ TC-LIST-02 + 变异 V4
- **训练营混入**：trainee 不按场次计（走赛季结算固定 XP），批量里必须整行拒绝而非静默跳过（静默跳过会让管理组以为录上了）。→ TC-BATCH-04 + 变异 V5
- **最大组**：一队花名册上限 = 在册 25 人 × 5 项全满，单批语句量 ≈ 2×项数 + 审计，验证整批一次成功且 changes 计数正确。→ TC-BATCH-09
- **rating 边界**：7.0 恰好记 1、6.9 拒、10.0 记 4；saves=8 记 1、saves=9 记 2（+1 额外）、duels=12 记 1。→ TC-BATCH-08
- **校验前置的原子性**：一批 3 条中 1 条非法 → 400 且**合法的 2 条也不落**（服务端先全量校验再开批，不是逐条写）。→ TC-BATCH-07
- **e2e 失败态**（铁律要求补失败态）：提交非法行 → 行内错误点名原因且不整页崩；列表无可补录比赛 → 空态文案。→ TC-UI-05 / TC-UI-06

## 用例

### TC-LIST 比赛列表（GET /match-entry）

**TC-LIST-01 · 只列可计 XP 的比赛**（P0 · vitest）
- 前置：result_confirmations 混插 4 场——league_premier 普通场、league_second 普通场、champions_cup group 场、champions_cup 淘汰轮场（stage_kind 非 group，competition_type=champions_cup）。
- 步骤：GET 列表。
- 预期：前 3 场出现、淘汰轮不出现。

**TC-LIST-02 · 弃权场与未确认比赛不出现**（P0 · vitest）
- 前置：walkover_side 非空的已确认场 ×1；只存在于 TOUR_DB、未确认的比赛 ×1。
- 步骤：GET 列表。
- 预期：两者都不出现；列表只来自 result_confirmations。

**TC-LIST-03 · 每场已录事件计数与排序**（P1 · vitest）
- 前置：A 场已录 3 条 growth_events（match_ref=比赛 id），B 场 0 条；确认时间 A 早于 B。
- 步骤：GET 列表。
- 预期：A 场 `recorded=3`、B 场 0；列表按确认时间倒序、默认 LIMIT 50。

**TC-LIST-04 · 两队 club 解析与 CPU/未建档标记**（P0 · vitest）
- 前置：主队=本库俱乐部名、客队名带 `(CPU)`；另插一场两队都解不开的。
- 步骤：GET 列表。
- 预期：第一场 homeClubId 有值、awayClubId=null 且标 CPU；第二场双侧 null 标未建档；列表仍出现（可录单侧）。

### TC-PANEL 单场面板（GET /match-entry/:matchId）

**TC-PANEL-01 · 花名册口径**（P0 · vitest）
- 前置：主队俱乐部有 normal×2、listed×1、trainee×1、free×1（free 不属该 club）；客队 1 人。
- 步骤：GET 面板。
- 预期：主队侧只出 normal/listed/trainee（trainee 带 status 标注），free 不出；两侧按 club 分组返回。

**TC-PANEL-02 · 已录事件预填**（P0 · vitest）
- 前置：该场球员 P1 自动已录 appearance+goal、P2 已录 rating 8.5。
- 步骤：GET 面板。
- 预期：返回该场 growth_events 按 player_id 分组；P1 的 appearance/goal、P2 的 rating 带值与来源，前端据此锁定。

**TC-PANEL-03 · matchId 不存在 / 未确认**（P1 · vitest）
- 步骤：GET /match-entry/999999。
- 预期：404。

### TC-BATCH 批量提交（POST /match-entry/:matchId）

**TC-BATCH-01 · 正常批量写入与 XP 正确**（P0 · vitest）
- 前置：一场联赛已确认，两队各 2 人。
- 步骤：POST entries——P1{appearance, rating 8.5}、P2{cleanSheet}、P3{duelsWon 24}、P4{saves 9}。
- 预期：201；written=5 条事件；growth_xp 增量 P1=2（1+2）、P2=0.5、P3=2、P4=2（1+1 额外）；season=可见赛季；source='manual'；recorded_by=操作者。

**TC-BATCH-02 · 越权球员 400**（P0 · vitest）
- 步骤：entries 带第三队球员 id。
- 预期：400「不属于该场两队」，零写入、零审计。

**TC-BATCH-03 · 训练营 400**（P0 · vitest）
- 步骤：entries 带 trainee 球员。
- 预期：400 点名该球员，零写入。

**TC-BATCH-04 · 口径复用单人规则**（P0 · vitest）
- 步骤：4 次提交——rating 6.9 / rating 10.5 / duelsWon 0 / saves -1。
- 预期：每次都 400，文案与现单人端点同口径（评分 7.0-10.0 / 次数正整数）；零写入。

**TC-BATCH-05 · 同锚去重（重复提交 no-op）**（P0 · vitest）
- 前置：先成功提交 P1{appearance, rating 8.0}。
- 步骤：同一 matchId 原样再提交一次。
- 预期：200；duplicates=2、written=0；P1 的 growth_xp **两次增量后不重复**；growth_events 仍各 1 行。

**TC-BATCH-06 · 与自动通道同锚去重**（P0 · vitest）
- 前置：该场自动钩子已写 P1 appearance（match_ref=比赛 id）。
- 步骤：POST P1{appearance, rating 9.0}。
- 预期：appearance 计 duplicate 不重复加 1 XP；rating 是新项正常入账 3 XP；written=1、duplicates=1。

**TC-BATCH-07 · 校验前置的原子性**（P0 · vitest）
- 步骤：一批 3 条，第 2 条 rating 6.0（非法）。
- 预期：400；合法的第 1、3 条也零落库（growth_events 与 growth_xp 均无变化）。

**TC-BATCH-08 · 边界值**（P0 · vitest）
- 步骤：rating 7.0（XP 1）/ rating 10.0（XP 4）/ duelsWon 12（1）/ duelsWon 11（0 → 400 不记 XP）/ saves 8（1）。
- 预期：逐项与 xpForEvent 一致；「达不到记 XP 标准」的单项提交 400（同单人端点语义）。

**TC-BATCH-09 · 最大组：整队 25 人×5 项全满**（P1 · vitest）
- 步骤：构造一队 25 人全项提交。
- 预期：一次 201；written=125 条；审计仅 1 条 growth_manual_event_batch，after 含 written/duplicates 汇总与逐人明细。

**TC-BATCH-10 · 审计与权限**（P0 · vitest）
- 步骤：匿名 POST → 401；管理员成功提交 → audit_log 恰 1 条 action='growth_manual_event_batch'、origin='user'、actor=管理员 id。
- 预期：如上；matchId 不存在 POST → 404。

### TC-UI 前端（e2e / 手动 / 纯函数单测）

**TC-UI-XP · 复算纯函数与 xpForEvent 同口径**（P0 · 单测）
- 步骤：对 web/src/lib/growth-xp.ts 断言与 src/worker/growth.ts 相同的输入输出表（appearance 1；rating 7/8/9/10 分档 1/2/3/4、6.9→0；goal/assist/clean_sheet 0.5；duels 12→1；saves 8→1、9→2）。
- 预期：全等；两侧注释互指。

**TC-UI-01 · 页面可达与列表渲染**（P1 · e2e）
- 步骤：管理员登录 → 侧栏「成长录入」→ /admin/growth。
- 预期：比赛列表出现，行内含对阵/比分/「已录 N 项」徽标。

**TC-UI-02 · 展开面板与行内编辑**（P1 · e2e）
- 步骤：点「录数据」→ 面板展开 → 主/客队 chip 切换 → 填一格评分。
- 预期：不跳页；本场 XP 列实时更新；chip 切换弹「未保存改动」确认。

**TC-UI-03 · 已录格子锁定**（P1 · 手动）
- 前置：该场有自动已录项。
- 预期：对应格子只读 +「已录」底色；进球/助攻列恒只读。

**TC-UI-04 · 保存回填与结算**（P1 · e2e）
- 步骤：填 2 行 → 全部保存。
- 预期：逐行「+X XP 新录」；顶栏合计「新录 N · 合计 +Y XP」；列表「已录 N 项」徽标刷新。

**TC-UI-05 · 失败态**（P0 · e2e）
- 步骤：填非法评分提交。
- 预期：行内点名原因（禁用态/红字），页面不崩；可修正后重提。

**TC-UI-06 · 空态与旧表单回归**（P2 · e2e）
- 步骤：无可补录比赛时打开页面；打开 /admin/players 成长引擎卡。
- 预期：空态文案；成长引擎卡**无**单人补录表单，档位核定/宣告成长期/赛季结算仍在。
